# 학습 노트 만들기

**목표는 글의 품질이다.**
대화 내용을 받아 적는 것이 아니라, 읽는 사람이 끝까지 읽고 "이해했다"와 "따라 해봤다"까지 갈 수 있는 글을 만든다.

`/note`가 호출되면 아래 절차를 순서대로 수행한다.
승인 전에는 어떤 경우에도 commit/push 하지 않는다.

---

## 1. 준비

### 1-1. 프로젝트 규칙 확인

`CLAUDE.md`를 읽고 파일명, Front Matter, 카테고리/태그, 문체, commit message 규칙을 확인한다.
이 문서와 충돌하면 `CLAUDE.md`를 우선한다. 날짜는 추측하지 말고 시스템 날짜를 쓴다.

### 1-2. 재료 점검

글을 쓰기 전에 다음을 확인한다.

* 대화에 글로 만들 만한 내용이 충분한가? 부족하면 추측으로 채우지 말고 **질문 1~2개**만 한다.
* `_posts/`에 같은 주제의 글이 있는가? 있으면 새 글 / 기존 글 수정 중 무엇이 나은지 묻는다.
* 한 글에 주제가 둘 이상인가? 그렇다면 분리를 제안한다.
* 기존 글 2~3개를 훑어 **이 블로그의 말투와 구성**을 파악하고 맞춘다.

### 1-3. 글의 방향 정하기 (쓰기 전에 한 줄씩 정한다)

| 항목 | 정할 내용 |
|------|-----------|
| 독자 | 누가 읽는가? (예: 이 개념을 처음 접하는 주니어, 6개월 뒤의 나) |
| 한 문장 요약 | 이 글을 읽고 나면 무엇을 알게 되는가? |
| 글의 유형 | 개념 설명 / 따라 하기 튜토리얼 / 트러블슈팅 / 비교 정리 / 회고 중 무엇인가? |
| 핵심 질문 | 이 글이 답하는 "왜?" 또는 "어떻게?"는 무엇인가? |

글의 유형에 따라 구조를 고른다. 모든 글에 같은 틀을 쓰지 않는다.

## 2. 글 쓰기: 품질 기준

### 2-1. 구조 (유형별)

**공통 뼈대**

1. **도입** : 문제 상황이나 궁금증으로 시작한다. (2~3문장, "이번에는 ~를 알아보겠습니다" 식의 인사말은 쓰지 않는다)
2. **TL;DR** : 결론부터 3줄 이내
3. 본문 (유형별, 아래 참고)
4. **정리** : 핵심 3가지와 다음에 볼 것
5. **참고 자료**

**본문 구성**

* **개념 설명** : 한 줄 정의 → 왜 필요한가 → 동작 원리 → 최소 예제 → 흔한 오해
* **튜토리얼** : 환경(버전) → 준비 → 단계별 실행 → 결과 확인 → 응용
* **트러블슈팅** : 증상(에러 메시지 원문) → 원인 → 해결 → 재발 방지
* **비교 정리** : 비교 기준을 먼저 제시 → 표 → 언제 무엇을 쓸지 결론

### 2-2. 깊이를 만드는 원칙

* **"무엇"보다 "왜"를 먼저 쓴다.** 명령어나 문법을 나열하지 말고, 그것이 생긴 이유와 동작 원리를 한 번은 설명한다.
* **구체적인 예시를 반드시 넣는다.** 추상적 설명 뒤에는 바로 실제 코드나 상황 예시를 붙인다.
* **비유는 한 번만, 정확하게 쓴다.** 억지 비유는 오히려 오해를 만든다.
* **Before / After를 보여준다.** 적용 전후의 차이가 보이면 설득력이 올라간다.
* **헷갈렸던 지점을 그대로 쓴다.** 내가 처음에 잘못 이해한 부분과 바로잡은 과정이 글의 가장 큰 가치다.
* **한계와 예외를 쓴다.** "항상 이렇다"고 단정하지 말고, 언제 안 되는지와 대안을 적는다.
* **하나의 글은 하나의 질문에 답한다.** 곁가지는 링크나 "더 알아보기"로 뺀다.

### 2-3. 코드와 명령어

* 코드 블록에는 항상 언어를 지정한다.
* **복사해서 바로 실행되는 코드**를 쓴다. 생략한 부분은 `# ... 생략` 으로 밝힌다.
* 가능하면 **최소 재현 예제**로 줄인다. 본질과 무관한 코드는 뺀다.
* 입력(`$ ...`)과 출력 결과를 별도 블록으로 구분한다.
* 실행해서 확인하지 않은 코드는 단정하지 않는다. 대화에서 확인되지 않았다면 `확인 필요`로 표시한다.
* 코드 주석은 짧은 것만 남기고, 긴 개념 설명은 본문으로 꺼낸다.
* 환경(OS, 언어, 도구, 라이브러리 **버전**)을 글 앞부분에 적는다.

### 2-4. 문장과 문체

* **첫 문장으로 독자를 붙잡는다.** 정의나 인사말 대신 문제, 질문, 결과로 시작한다.
* **한 문장에 하나의 내용만** 담는다. 길어지면 나눈다.
* 한 문단은 3~4문장 이내로 쓴다.
* 소제목은 **내용을 알 수 있게** 쓴다. (`개요`, `정리`만 쓰지 않는다. 예: `왜 rebase하면 커밋 해시가 바뀔까?`)
* 처음 등장하는 용어는 한 줄로 풀어 쓰고, 약어는 풀네임을 병기한다.
* 중요한 부분만 **굵게** 쓴다. 한 화면에 굵은 글씨가 3곳을 넘지 않게 한다.
* 종결어미(`~다` / `~해요`)를 글 전체에서 통일한다.

**피해야 할 표현** (AI가 쓴 티가 나거나 정보가 없는 문장)

* "이번 글에서는 ~에 대해 알아보겠습니다"
* "~는 매우 중요합니다", "~는 필수적입니다" (왜 중요한지 없이)
* "다양한", "효율적인", "강력한" 같은 근거 없는 수식어
* 같은 내용을 반복하는 마무리 ("결론적으로 위에서 말한 것처럼…")
* 이모지 남발, 과한 느낌표

### 2-5. 정확성과 출처

* 사용자가 말한 **의미를 바꾸지 않는다.**
* 사용자가 말하지 않은 내용을 보충했다면, 초안을 보여줄 때 **어디를 보충했는지** 알린다.
* 확신이 없는 내용은 단정하지 말고 `확인 필요`로 표시해 묻는다.
* 버전에 따라 달라지는 내용은 버전을 함께 적는다.
* 공식 문서로 확인할 수 있는 내용은 **링크를 남긴다.**
* 다른 글이나 문서의 표현을 그대로 옮기지 않는다.

### 2-6. 보안 / 개인정보

다음이 있으면 **마스킹하거나 제거**한다.

* API 키, 토큰, 비밀번호, `.env` 값
* 내부 서버 주소, 사내 프로젝트명, 개인 이메일
* 로컬 경로의 사용자명 (`/Users/홍길동/...` → `~/...`)

## 3. 셀프 리뷰 (초안을 보여주기 전에 두 번 읽는다)

### 3-1. 독자 시점으로 읽기

글을 처음 보는 독자라고 가정하고 확인한다.

* 제목과 TL;DR만 읽어도 **이 글을 읽을지 판단**할 수 있는가?
* 처음 나오는 용어나 전제 지식을 설명 없이 쓴 곳이 있는가?
* 중간에 **논리가 건너뛰는 곳**이 있는가? ("그래서 왜?"가 떠오르는 곳)
* 예제를 따라 하다 막힐 만한 곳이 있는가? (버전, 준비 단계, 생략된 설정)
* 빼도 되는 문단이 있는가? 있으면 뺀다.

### 3-2. 문장 검토

* 주어와 서술어가 자연스럽게 연결되는가?
* 목적어, 보어 등 필요한 문장 성분이 빠지지 않았는가?
* 조사와 어미가 자연스러운가?
* 같은 표현이 불필요하게 반복되지 않았는가?
* 구어체가 학습 노트에 맞는 문체로 정리되었는가?
* 2-4의 **피해야 할 표현**이 남아 있지 않은가?

다음 **요약 표현은 완전한 문장이 아니어도 허용**한다.

* `A → B`, `A : B`, `명령어 : 설명`
* 표 안의 짧은 키워드, 코드, 짧은 목록 항목

**의도한 요약 표현과 문장 오류를 구분해서** 오류만 수정한다.

### 3-3. Markdown 및 표 검수

* 제목 계층이 건너뜀 없이 이어지는가?
* 코드 블록이 모두 닫혀 있는가?
* 표의 헤더가 모두 있고, 각 행의 열 개수가 같은가?
* 표 안의 `|` 가 구조를 깨뜨리지 않는가? (필요하면 `\|`)
* 빈 셀이 남아 있는가? 의미 없는 빈 셀은 내용을 채우고, 의도적으로 "없음"이면 `-` 로 쓴다.
* 링크가 깨지지 않았는가?
* `{{ }}`, `{% %}` 때문에 Jekyll 렌더링이 깨지지 않는가? (필요하면 `{% raw %}`)

## 4. 파일 생성

검수가 끝나면 `CLAUDE.md` 규칙에 따라 `_posts/`에 파일을 생성한다.

* 파일 경로와 파일명이 규칙에 맞는가?
* Front Matter가 `---` 로 열리고 닫혔는가?
* `title`은 검색 키워드를 포함하는가? `description`이 있다면 1~2문장으로 글의 가치를 설명하는가?
* `categories`, `tags`는 기존 값을 재사용하는가?
* 가능하면 로컬 빌드(`bundle exec jekyll build` 등)로 오류를 확인한다. 불가능하면 생략하고 그 사실을 알린다.

## 5. 사용자에게 초안 보여주기

**이 단계에서는 절대 commit/push 하지 않는다.**

다음을 순서대로 보여준다.

1. 생성한 파일 경로
2. 글 전체 내용
3. **검수 요약** (5줄 이내)
   * 정한 독자와 글의 유형
   * 사용자 말 외에 **내가 보충한 부분**
   * `확인 필요`로 표시한 부분
   * 마스킹한 정보, 빌드 결과
   * 더 보강하면 좋을 점 (예: "실행 결과 스크린샷이 있으면 좋아요")

안내 문구

> 학습 노트 초안을 작성했어.
> 내용을 확인해줘. 수정할 곳이 없으면 `굿`, `ㄱㄱ`, `커풋` 중 하나로 알려줘. 그러면 commit하고 push할게.

수정 요청을 받으면 다음 순서로 처리한다.

1. 파일을 수정한다.
2. 수정한 곳만이 아니라 **전체 글을 다시 검수**한다. (3번 단계)
3. 수정본 전체를 다시 보여준다.
4. 다시 승인을 기다린다.

---

## 6. 승인 후 Git 작업

승인을 받은 경우에만 수행한다.

1. `git status`, `git diff`로 변경사항을 확인한다.
2. 이번 작업의 파일만 `git add <파일>` 로 staging 한다. (`git add .`, `git add -A` 금지)
3. `CLAUDE.md` 또는 기존 `git log`의 규칙에 맞춰 commit message를 쓴다. 규칙이 없으면 다음 형식을 쓴다.
   ```bash
   docs: add study note about Git branching
   ```
4. commit 한다.
5. branch와 remote를 확인한 뒤 push 한다.
6. push가 실패하면 임의로 해결하지 말고 상황을 설명하고 묻는다.

금지: `git push --force` 계열, `--no-verify`, 무관한 파일 commit

# 승인 판정 규칙

**승인으로 인정하는 표현**

* `굿`
* `ㄱㄱ`
* `커풋`

**승인으로 인정하지 않는 표현**

* `음`, `오`, `괜찮은데`, `거의 좋아`
* `여기만 수정해줘`, `다른 건?`
* 승인 표현과 수정 요청이 **함께 있는 경우** (예: `굿인데 제목만 바꿔줘`)

승인이 불명확하면 commit/push 하지 말고 한 번 더 묻는다.
승인은 **직전에 보여준 초안**에만 유효하다. 수정했다면 다시 받는다.

# 최종 체크리스트

**내용**
- [ ] 독자와 글의 유형을 정했고, 한 문장으로 요약할 수 있다
- [ ] "왜"를 설명했고, 구체적인 예시가 있다
- [ ] 헷갈렸던 점, 한계, 예외를 적었다
- [ ] 환경과 버전, 출처 링크가 있다

**문장**
- [ ] 첫 문장이 독자를 붙잡는다
- [ ] 정보 없는 문장과 상투적 표현이 없다
- [ ] 문장 성분과 문체가 통일되어 있다

**형식**
- [ ] 코드 블록 언어 지정, 실행 가능 여부 확인
- [ ] 표의 빈 셀과 열 개수 확인
- [ ] 민감 정보 마스킹

**절차**
- [ ] 초안을 먼저 보여줬다
- [ ] 명확한 승인 후에만 commit/push 했다
