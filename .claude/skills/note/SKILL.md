# 학습 노트 만들기

`/note`가 호출되면 아래 절차를 **순서대로 반드시 수행한다.**

## 1. 프로젝트 규칙 확인

먼저 프로젝트의 `CLAUDE.md`를 읽고 다음 내용을 확인한다.

* `_posts/`의 글 작성 규칙
* 파일명 규칙
* Front Matter 형식
* 카테고리 및 태그 규칙
* 글의 문체 및 Markdown 작성 규칙
* 기타 블로그 관련 규칙

`CLAUDE.md`에 명시된 규칙이 있으면 이 규칙을 최우선으로 따른다.

---

## 2. 학습 내용 정리

사용자가 이번 대화에서 알려준 내용을 바탕으로 학습 노트를 작성한다.

단순히 사용자의 문장을 그대로 옮기지 말고, **나중에 다시 읽었을 때 복습할 수 있는 형태**로 정리한다.

다음 원칙을 따른다.

### 내용 구성

가능하면 다음 흐름을 사용한다.

1. 무엇을 배웠는지
2. 왜 필요한지
3. 핵심 개념
4. 실제로 어떻게 사용하는지
5. 사용하면서 알게 된 점
6. 주의할 점
7. 정리 / 회고

단, 학습 내용에 맞지 않는 항목은 억지로 추가하지 않는다.

### 문장 작성

작성한 모든 문장을 다음 기준으로 검토한다.

* 주어와 서술어가 자연스럽게 연결되는가?
* 목적어, 보어 등 필요한 문장 성분이 빠지지 않았는가?
* 조사와 어미가 자연스러운가?
* 같은 표현을 불필요하게 반복하지 않았는가?
* 구어체 표현이 학습 노트에 적절한 문체로 정리되었는가?
* 사용자가 말한 의미를 임의로 바꾸지 않았는가?

단, 다음과 같은 **요약 표현은 완전한 문장이 아니어도 허용한다.**

* `A → B`
* `A : B`
* `명령어 : 설명`
* 표 안의 짧은 키워드
* 코드
* 목록의 짧은 항목

즉, **의도적인 요약 표현과 문장 오류를 구분해서 검토한다.**

---

## 3. Markdown 및 표 검수

글을 완성한 뒤 Markdown 구조를 확인한다.

특히 표(table)는 반드시 다음을 확인한다.

* 헤더가 모두 작성되어 있는가?
* 각 행의 열 개수가 동일한가?
* 빈 셀이 의도된 것인지 확인했는가?
* 실수로 누락된 내용이 없는가?
* `|` 문자가 잘못 들어가 표 구조가 깨지지 않는가?
* 코드나 특수문자로 인해 Markdown이 깨지지 않는가?

**의미 없이 비어 있는 셀은 남기지 않는다.**

---

## 4. 파일 생성

검수가 끝나면 `CLAUDE.md`의 규칙에 따라 `_posts/`에 학습 노트 파일을 생성한다.

파일명과 Front Matter는 반드시 `CLAUDE.md` 규칙을 따른다.

파일을 생성한 뒤 다음을 다시 확인한다.

* 파일 경로가 올바른가?
* 파일명이 규칙에 맞는가?
* Front Matter가 정상적으로 닫혀 있는가?
* Markdown 문법이 깨지지 않았는가?
* 표에 빈 셀이 남아 있지 않은가?
* 문장 오류가 없는가?

---

## 5. 사용자에게 초안 먼저 보여주기

**이 단계에서는 절대 커밋하거나 push하지 않는다.**

작성한 학습 노트의 전체 내용을 사용자에게 먼저 보여준다.

다음과 같이 안내한다.

> 학습 노트 초안을 작성했어.
> 내용을 확인해줘. 수정할 부분이 없고 "좋아", "커밋해", "push해" 등으로 승인하면 커밋하고 push할게.

사용자가 수정 요청을 하면:

1. `_posts/`의 파일을 수정한다.
2. 수정된 전체 내용을 다시 검토한다.
3. 수정본을 사용자에게 보여준다.
4. 다시 승인을 기다린다.

**사용자가 명확하게 승인하기 전까지 절대 commit/push하지 않는다.**

---

## 6. 사용자 승인 후 Git 작업

사용자가 명확하게 승인한 경우에만 Git 작업을 수행한다.

순서는 다음과 같다.

1. 변경된 파일 확인
2. `git diff`로 최종 변경사항 확인
3. 필요한 파일만 staging
4. 적절한 commit message 작성
5. commit
6. 현재 branch 및 remote 확인
7. push

가능하면 commit message는 학습 내용이 드러나도록 작성한다.

예:

```bash
docs: add study note about Git branching
```

또는 프로젝트의 기존 commit message 규칙이 있다면 해당 규칙을 따른다.

---

## 7. Git 작업 결과 확인

commit과 push가 끝나면 결과를 확인한다.

최종적으로 사용자에게 다음 내용을 간단하게 알려준다.

* 작성된 파일
* commit 완료 여부
* push 완료 여부
* commit message

# 중요 규칙

### 반드시 지킬 것

* `CLAUDE.md`를 먼저 확인한다.
* `_posts/`에 작성한다.
* 문장 구조를 검수한다.
* 의도적인 요약 표현과 문장 오류를 구분한다.
* table의 빈 셀과 Markdown 오류를 검사한다.
* 사용자가 승인하기 전에는 **절대 commit하지 않는다.**
* 사용자가 승인하기 전에는 **절대 push하지 않는다.**
* 수정 요청이 들어오면 수정 후 다시 전체 내용을 보여준다.
* 승인 후에만 Git 작업을 수행한다.

### 승인으로 간주할 수 있는 표현

다음과 같이 사용자가 명확하게 최종 승인을 표현한 경우 Git 작업을 진행한다.

* `굿`
* `ㄱㄱ`
* `커풋`

단순히 다음과 같은 표현은 승인으로 간주하지 않는다.

* `음`
* `오`
* `괜찮은데`
* `거의 좋아`
* `여기만 수정해줘`
* `다른 건?`

수정 의도가 포함되어 있거나 승인이 불명확하면 계속 사용자 확인을 기다린다.
