`static` 리스트에 회원을 담아 두면 서버를 재시작해도 남아 있을까? 개념을 읽을 때는 답이 뻔해 보이지만, 선택지로 주어지면 헷갈리는 곳이 드러난다.  
[DB가 필요한 이유]({{ site.baseurl }}/database-why-needed.html)에서 정리한 내용을 다섯 문제로 확인한다.  
각 문제의 정답과 해설은 `정답 보기`를 눌러 확인한다.

> **TL;DR**
> - 지역변수, 객체, `static` 변수는 수명이 달라도 JVM이 꺼지면 모두 사라진다.
> - 서버마다 저장소가 따로 있으면 데이터가 나뉘고, 하나의 DB를 공유하면 해결된다.
> - 트랜잭션은 "전부 성공 아니면 전부 취소"를 보장하고, 객체 하나는 테이블의 행 하나에 대응한다.

## 문제 1. 지역변수는 언제 사라질까

메서드 안에서 선언한 지역변수는 언제 사라질까?

1. 메서드 실행이 끝날 때
2. GC가 실행될 때
3. JVM이 종료될 때
4. 사라지지 않는다

<details markdown="1">
<summary>정답 보기</summary>

**정답: 1번**

지역변수는 Stack의 프레임 안에 산다. 메서드가 끝나 프레임이 제거되면 함께 사라진다.

헷갈리기 쉬운 오답은 2번이다. GC(가비지 컬렉터)는 Heap의 객체를 회수하는 장치여서 Stack의 지역변수와는 관계가 없다.  
3번은 틀린 말은 아니지만, 지역변수는 그보다 훨씬 일찍 사라지므로 "언제"에 대한 답이 되지 못한다.

</details>

## 문제 2. static 리스트에 담은 회원은 재시작 후 어떻게 될까

회원 목록을 `static List<Member>`에 저장했다. 새 버전을 배포하며 서버를 재시작하면 어떻게 될까?

1. `static`이라서 그대로 남는다
2. JVM이 종료되면서 함께 사라진다
3. 자동으로 파일에 저장된다
4. GC 대상이 아니므로 남는다

<details markdown="1">
<summary>정답 보기</summary>

**정답: 2번**

`static` 변수는 지역변수나 일반 객체보다 오래 살지만, 수명의 끝은 JVM 종료다.  
JVM이 꺼지면 OS가 그 프로세스의 메모리를 전부 회수한다. 재시작한 JVM의 리스트는 비어 있다.

1번과 4번은 "오래 산다"와 "영원히 산다"를 혼동한 오답이다. 3번처럼 메모리의 내용을 자동으로 파일에 옮겨 주는 기능은 없다.

</details>

## 문제 3. 서버 2대가 각자 파일에 저장하면 어떤 문제가 생길까

서버 2대가 각자 자기 파일에 회원을 저장하면 어떤 문제가 생길까?

1. 파일 저장 속도가 너무 빨라진다
2. 서버 A에서 가입한 회원이 서버 B에서는 없는 회원이 된다
3. 컴파일 에러가 난다
4. 아무 문제 없다

<details markdown="1">
<summary>정답 보기</summary>

**정답: 2번**

서버마다 저장소가 따로 있으면 데이터가 나뉜다. 서버 A의 파일에 쓴 회원을 서버 B는 볼 수 없다.  
모든 서버가 하나의 DB에 접속해 함께 쓰면 이 문제가 해결된다.

파일에 저장하면 재시작해도 데이터가 남으므로 문제 2의 해결책처럼 보이지만, 서버가 여러 대가 되는 순간 이 방식은 한계에 부딪힌다.

</details>

## 문제 4. 계좌이체 도중 서버가 멈춰도 보장되는 기능은

계좌이체 도중 서버가 멈춰도 "전부 성공 아니면 전부 취소"를 보장하는 DB 기능은?

1. 인덱스(Index)
2. 트랜잭션(Transaction)
3. 정렬(`ORDER BY`)
4. 반복문(`for`)

<details markdown="1">
<summary>정답 보기</summary>

**정답: 2번**

트랜잭션은 여러 작업을 하나로 묶는 기능이다.  
끝까지 성공하면 `COMMIT`으로 확정하고, 중간에 실패하면 `ROLLBACK`으로 되돌린다.

예를 들어 "A 계좌에서 출금"만 끝나고 "B 계좌에 입금" 전에 서버가 멈추면 돈이 사라진 채로 남는다. 트랜잭션은 이런 중간 상태를 남기지 않는다.  
인덱스는 검색을 빠르게 하는 장치이고, 정렬은 결과의 순서를 정하는 구문이어서 작업의 성공과 취소와는 관계가 없다. 반복문은 DB 기능이 아니라 프로그래밍 언어의 문법이다.

</details>

## 문제 5. 객체 하나는 DB에서 무엇에 해당할까

Java의 객체(인스턴스) 하나는 DB 테이블에서 무엇에 해당할까?

1. 테이블
2. 컬럼(Column)
3. 행(Row)
4. 데이터베이스

<details markdown="1">
<summary>정답 보기</summary>

**정답: 3번**

클래스는 테이블, 필드는 컬럼, 객체 하나는 행 하나에 대응한다.

"객체"라는 말에 끌려 1번을 고르기 쉽다. 하지만 테이블은 같은 모양의 데이터를 모아 둔 틀이므로 객체가 아니라 클래스에 가깝다.

</details>

## 정리

- 1, 2번은 JVM 메모리 영역의 수명이다. 지역변수는 메서드가 끝날 때, `static` 변수는 JVM이 종료될 때 사라진다.
- 3, 4번은 DBMS가 해결하는 문제다. 서버가 여러 대여도 데이터를 하나로 모으고, 작업 도중 실패해도 중간 상태를 남기지 않는다.
- 5번은 객체와 테이블의 대응이다. 클래스는 테이블, 필드는 컬럼, 객체는 행이다.

틀린 문제가 있으면 [DB가 필요한 이유]({{ site.baseurl }}/database-why-needed.html)의 해당 절을 다시 읽는다. 다음에 볼 것은 [SELECT 기초]({{ site.baseurl }}/mysql-select-basics.html)다.

## 더 학습하면 좋은 개념

- **JVM 런타임 데이터 영역(Stack, Heap, Method Area)** — 1, 2번의 수명 차이가 어느 영역에 저장되는지에서 갈린다. 영역을 구분하면 변수가 언제 사라지는지 예측할 수 있다.
- **ACID** — 트랜잭션이 보장하는 네 가지 성질(원자성, 일관성, 격리성, 지속성)이다. "전부 성공 아니면 전부 취소"는 그중 원자성에 해당한다.
- **인덱스(Index)** — 문제 4의 오답 선택지였지만 DB의 핵심 기능이다. 데이터가 많을 때 검색 속도가 왜 달라지는지 이해할 수 있다.
- **ORM(Object-Relational Mapping)** — 문제 5의 객체와 테이블 대응을 자동으로 처리해 주는 기술이다. 대응 관계를 알아야 JPA 같은 도구가 하는 일을 이해할 수 있다.
