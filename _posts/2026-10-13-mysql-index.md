`users` 테이블에 100만 명이 들어 있고, 그중에서 `홍길동`이라는 사람을 찾아야 한다.  
인덱스가 없으면 데이터베이스는 첫 번째 행부터 마지막 행까지 하나씩 비교하며 찾는다.  
이 비용을 줄이는 도구가 인덱스이고, 대신 무엇을 내줘야 하는지까지 실습한 내용으로 정리했다.

> **TL;DR**
> - 인덱스가 없으면 조건에 맞는 행을 찾기 위해 테이블 전체를 훑는다(full table scan). 인덱스는 컬럼 값과 데이터의 물리적 위치를 미리 정리해 둔 목차다.
> - `EXPLAIN`으로 실행 계획을 확인하면, `CREATE INDEX` 전에는 120개 row를 full scan했고 후에는 1개 row만 scan했다.
> - 인덱스는 저장 공간을 쓰고 INSERT, UPDATE, DELETE를 느리게 한다. 조회가 압도적으로 많고 수정이 드문 컬럼에만 건다.

환경: MySQL (버전 `확인 필요`). 실습 테이블은 `users`이고, 쿼리 결과는 실습에서 확인한 scan 건수만 옮겼다.

## 인덱스가 없으면 어떻게 찾을까

데이터베이스는 데이터를 조회할 때 첫 번째 행부터 마지막 행까지 하나씩 비교하면서 스캔한다. 이를 **full table scan**이라고 한다.

100만 명 중 홍길동을 찾는다면 최악의 경우 100만 번을 비교한다. 홍길동이 한 명뿐이어도 마지막 행까지 가봐야 더 없다는 것을 알 수 있다. 데이터가 늘수록 조회가 느려지는 이유다.

## 인덱스는 숫자 번호가 아니라 목차다

처음에 인덱스를 보고 배열의 `0, 1, 2...`처럼 0부터 시작하는 숫자 번호를 떠올리기 쉽다. 하지만 데이터베이스에서 인덱스는 숫자 체계가 아니라 **목차**라는 뜻이다.

특정 컬럼의 값과 해당 데이터의 물리적 위치를 미리 목차 형태로 만들어 저장해 둔다. 이렇게 해두면 쿼리를 실행할 때 목차를 통해 원하는 데이터의 위치로 바로 이동할 수 있어서 검색 속도가 빨라진다.

| 구분 | 인덱스가 없을 때 | 인덱스가 있을 때 |
|------|------------------|------------------|
| 찾는 방식 | 첫 행부터 마지막 행까지 하나씩 비교 | 목차에서 위치를 찾아 바로 이동 |
| 이름 | full table scan | 인덱스를 통한 조회 |

## EXPLAIN으로 실행 계획 확인하기

인덱스가 실제로 효과가 있는지는 `EXPLAIN`으로 확인한다. `EXPLAIN`은 쿼리를 실제로 처리하기 전에 MySQL이 어떤 방식으로 실행할 계획인지 보여준다.

```sql
explain select * from users where name = '홍길동';
```

> **보충**: 아래 컬럼 설명은 [MySQL 공식 문서의 EXPLAIN Output Format](https://dev.mysql.com/doc/refman/8.0/en/explain-output.html)을 근거로 짧게 정리했다.

| 컬럼 | 의미 |
|------|------|
| `type` | 테이블을 읽는 방식(join type). `ALL`이면 테이블 전체를 읽는 full table scan이다 |
| `key` | 실제로 선택해 사용한 인덱스 |
| `rows` | 쿼리를 실행하기 위해 검사해야 한다고 MySQL이 추정한 행 수 |

`rows`는 실제 건수가 아니라 추정치라는 점에 주의한다.

## 인덱스 생성 전후 비교

인덱스는 `create index 인덱스이름 on 테이블명(적용할 컬럼명)` 형식으로 만든다. `users`의 `name` 컬럼에 인덱스를 만들었다.

```sql
create index idx_users_name on users(name);
```

만든 뒤 같은 `EXPLAIN`을 다시 실행했다.

```sql
explain select * from users where name = '홍길동';
```

| 구분 | 인덱스 적용 전 | 인덱스 적용 후 |
|------|----------------|----------------|
| 쿼리 | `explain select * from users where name = '홍길동';` | 동일 |
| scan한 row | 120개를 full scan | 1개만 scan |

쿼리는 한 글자도 바꾸지 않았는데 scan 대상이 120개에서 1개로 줄었다. 쿼리를 고치지 않고 인덱스만 추가해도 실행 계획이 달라진다는 점이 인상적이었다.

## 인덱스의 단점: 양날의 검

인덱스는 양날의 검이고, 얻는 것만큼 내주는 것이 있다(trade-off). 단점은 두 가지다.

### 1. 저장 공간 비용

인덱스는 테이블 데이터와 별도의 공간을 차지하는 데이터 구조체다. 책으로 치면 목차가 10~20쪽을 차지하는 것과 같다. 인덱스를 많이 만들수록 전체 용량이 커진다.

### 2. INSERT, UPDATE, DELETE 성능 저하

더 중요한 단점이다. 인덱스는 SELECT 성능은 높이지만 데이터를 변경하는 작업(DML)의 성능은 떨어뜨린다.

| 작업 | 인덱스가 있을 때 추가로 필요한 일 |
|------|-----------------------------------|
| INSERT | 새 데이터를 추가할 때 인덱스에서도 정렬된 위치를 찾아 새 항목을 추가해야 한다 |
| DELETE | 테이블에서 데이터를 지울 때 인덱스에서도 해당 항목을 찾아 삭제해야 한다 |
| UPDATE | 인덱스가 걸린 컬럼의 값을 수정하면 최악이다. 기존 항목 삭제와 새 항목의 정렬된 위치 삽입이 함께 발생한다 |

UPDATE는 인덱스 입장에서 삭제와 삽입이 동시에 일어나는 작업이다. 그래서 자주 수정되는 컬럼에 인덱스를 걸면 손해가 커진다.

## 어떤 컬럼에 인덱스를 걸까

위 단점을 기준으로 적용 대상을 고르는 기준은 두 가지다.

1. **조회 비율이 압도적으로 높은 테이블**: DML 작업에서 지연이 생기더라도 감수할 수 있어야 한다.
2. **DML 중에서도 수정이 빈번하지 않은 컬럼**: 위에서 본 UPDATE의 삭제와 삽입 비용을 피할 수 있다.

## PK와 UNIQUE는 이미 인덱스가 있다

PK(기본 키)와 UNIQUE 제약 조건이 걸린 컬럼은 데이터의 유일성이 보장되어야 한다. 그래서 테이블을 만들 때 **자동으로 인덱스가 적용된다.** 이런 컬럼에 `create index`를 또 만들 필요는 없다.

## 정리

- 인덱스가 없으면 full table scan이라 데이터가 늘수록 느려지고, 인덱스는 숫자 번호가 아니라 값과 물리적 위치를 담은 목차다.
- `EXPLAIN`으로 전후를 확인한다. 이번 실습에서는 `create index idx_users_name on users(name);` 하나로 120개 row full scan이 1개 row scan으로 줄었다.
- 인덱스는 저장 공간과 DML 성능을 내주는 대가다. 조회가 압도적으로 많고 수정이 드문 컬럼에 건다.

다음에는 하나의 인덱스가 어떤 구조로 저장되는지, 그리고 인덱스를 걸어도 쓰이지 않는 쿼리가 있는지 살펴보려 한다.

## 더 학습하면 좋은 개념

- **B-Tree 인덱스 구조** — 목차가 정렬된 형태로 저장되는 방식이다. 왜 INSERT 때 정렬된 위치를 찾아야 하는지 이해하는 바탕이 된다.
- **복합 인덱스(Composite Index)** — 컬럼 여러 개를 묶어 만드는 인덱스다. 조건이 여러 컬럼에 걸린 쿼리에서 어떤 순서로 만들어야 하는지 판단하는 기준이 된다.
- **카디널리티(Cardinality)** — 컬럼에 들어 있는 값의 종류가 얼마나 다양한가를 뜻한다. 값이 몇 종류뿐인 컬럼에는 인덱스가 효과가 적을 수 있어서 대상 선정에 쓰인다.
- **인덱스를 타지 않는 쿼리** — 인덱스를 만들어도 쿼리 작성 방식에 따라 쓰이지 않을 수 있다. `EXPLAIN`의 `key`로 확인하는 습관의 근거가 된다.
