주문 한 건에 메뉴가 세 개 들어 있다. 주문 테이블에 `menu_code` 칸을 하나만 두면 주문 한 건이 세 행이 되고, 주문번호가 반복되어 기본키로 쓸 수 없다. 이런 문제는 테이블을 만들기 전에 **엔티티와 관계를 제대로 정하는 개념적 모델링**에서 풀어야 한다.

> **TL;DR**
> - 엔티티는 식별 가능하고, 여러 인스턴스가 있고, 의미 있는 속성이 있고, 독립적으로 존재해야 한다.
> - 관계는 유형(1:1, 1:N, N:M)과 필수성(최소값 0 또는 1)으로 정의하고, N:M은 교차 엔티티로 해소한다.
> - ERD는 실무에서는 IE(Crow's Foot) 표기법을 많이 쓰고, 그린 뒤에는 체크리스트로 품질을 검토한다.

환경: MySQL, ERDCloud(웹 ERD 도구). 예시 DB는 수업에서 쓰는 `menudb`다. 같은 날 정리한 [설계 1편]({{ site.baseurl }}/db-design-requirements-constraints.html)에서 이어진다.

## 1. 엔티티는 어떻게 찾을까?

엔티티(Entity)는 시스템에서 저장하고 관리할 데이터의 주체가 되는 객체다. 사람, 사물, 사건, 장소가 모두 엔티티가 될 수 있다. 아래 네 가지를 만족해야 한다.

| 엔티티의 요건 | 의미 |
|---------------|------|
| 식별 가능 | 고유하게 구분할 식별자가 있어야 한다 |
| 여러 인스턴스 | 같은 종류의 데이터가 여러 건 존재할 수 있어야 한다 |
| 의미 있는 속성 | 관리할 가치가 있는 속성이 있어야 한다 |
| 독립적 존재 | 독립적으로 존재할 수 있어야 한다 |

수업에서 쓰는 `menudb`의 테이블을 엔티티 관점으로 보면 이렇다.

| 테이블명 | 엔티티명 | 역할 |
|----------|----------|------|
| `tbl_menu` | 메뉴 (Menu) | 실제 판매되는 개별 상품 항목 |
| `tbl_category` | 카테고리 (Category) | 메뉴 분류 체계 |
| `tbl_order` | 주문 (Order) | 고객의 구매 행위 |
| `tbl_order_menu` | 주문상세 (OrderItem) | 주문별 메뉴 항목 |
| `tbl_payment` | 결제 (Payment) | 결제 정보 기록 |
| `tbl_payment_order` | 결제연결 (PaymentMap) | 결제와 주문 간 관계 매핑 |

상태 코드처럼 단순 참조용 테이블은 반드시 독립 엔티티로 만들 필요가 없다. 화면 설계서가 있다면 각 화면의 주제 객체가 엔티티 후보일 가능성이 높다.

### 요구사항 문장에서 엔티티를 고르는 4단계

도서관 대출 시스템을 예로 들면 다음 순서로 진행한다.

1. 핵심 명사 추출 : 회원, 대출일, 도서관, 제목, 대출, 연락처, 도서, 반납일, 저자
2. 유사 용어 통합 : 같은 뜻의 용어를 하나로 합친다
3. 엔티티 여부 판단 : 남은 명사마다 위 요건 4가지를 따진다
4. 엔티티 확정

판단 결과는 아래와 같다.

| 명사 | 분류 | 이유 |
|------|------|------|
| 회원 | 엔티티 | 여러 명이고 회원번호로 식별되며 이름, 연락처 같은 속성이 있다 |
| 도서 | 엔티티 | 여러 권이고 도서번호로 식별되며 제목, 저자 같은 속성이 있다 |
| 대출 | 엔티티 | '빌린다'는 사건이 여러 번 일어나고, 대출일·반납일 속성이 있으며 회원과 도서 사이의 행위를 기록한다 |
| 연락처, 대출일, 반납일, 제목 | 속성 | 회원, 대출, 도서를 설명하는 값이다 |
| 저자 | 속성 | 도서를 설명하는 값이다. 저자 정보를 따로 관리해야 하는 업무라면 엔티티로 승격될 수 있다 |
| 도서관 | 제외 | 이 시스템에서는 도서관이 하나뿐이라 인스턴스가 여러 개가 아니다 |

### 헷갈렸던 점: 게시판 요구사항에서는 무엇이 엔티티일까?

수업에서 다룬 게시판 요구사항이다.

> 사용자는 회원 번호, 아이디, 패스워드, 닉네임, 회원가입 일자를 가지고 회원가입할 수 있다. 회원은 게시글을 작성할 수 있으며, 게시글은 작성자, 제목, 내용, 작성일로 구성된다. 게시글에는 댓글을 달 수 있으며, 내용, 작성자, 수정여부, 작성 일시가 있다. 댓글에는 답글을 달 수 있다.

ERD 초안에서는 엔티티(오렌지)와 속성(블루)을 색으로 구분해 표시했다.

| 구분 | 항목 |
|------|------|
| 엔티티 | 사용자(회원), 게시글, 댓글, 대댓글 |
| 속성 | 회원번호, 아이디, 비밀번호, 닉네임, 회원가입일자, 작성자, 제목, 내용, 작성일, 수정여부 |

여기서 대댓글은 댓글과 구조가 같으므로 **댓글 = 대댓글로 처리하고 대댓글 엔티티는 삭제**한다. 대신 부모 댓글이 무엇인지를 담는 값을 둔다. 수업의 예시는 이렇다.

| 댓글번호 | 내용 | 부모 댓글번호 |
|----------|------|---------------|
| 1 | 댓글 내용 | NULL |
| 2 | 댓글 내용 2 | 1 |

부모가 없으면 NULL, 답글이면 부모 댓글번호를 넣는다. 게시글 번호와 댓글번호처럼 각 행을 구별할 수 있는 값도 추가한다.

### 엔티티는 어떤 성격으로 나눌까?

| 분류 | 성격 | `menudb` 예시 |
|------|------|---------------|
| 기본 엔티티 (Master) | 다른 데이터의 기준이 되는 고정적 객체. 여기저기서 참조되어 참조 엔티티라고도 한다 | 카테고리, 메뉴 |
| 중심 엔티티 (Core) | 주요 거래나 사건의 중심이 되는 객체 | 주문, 결제 |
| 행위 엔티티 (Transaction) | 중심 엔티티 간의 관계나 발생한 사건을 표현. 행위의 결과(history)를 저장하기도 한다 | 주문상세, 결제연결 |

## 2. 엔티티 사이의 관계는 어떻게 정의할까?

관계는 "어떻게 연결되는지, 몇 개씩 연결되는지, 연결이 반드시 있어야 하는지"를 정하는 일이다. 관계는 **양방향**으로 읽어야 한다. 회원 → 주문은 한 명의 회원이 여러 주문을 할 수 있고, 주문 → 회원은 한 건의 주문 입장에서 회원이 한 명이다.

### 관계 유형: 1:1, 1:N, N:M

| 유형 | 설명 | 예시 |
|------|------|------|
| 1:1 | 한 인스턴스가 상대 인스턴스 하나와만 연결된다. 보안 분리나 선택 정보 분리 목적에 주로 쓴다 | 사용자 ↔ 사용자프로필 |
| 1:N | 한 인스턴스가 여러 인스턴스와 연결된다. 가장 흔하다 | 카테고리 ↔ 메뉴, 회원 ↔ 게시글 |
| N:M | 여러 개와 여러 개가 연결된다. 관계 자체를 교차 엔티티로 만들어 해소한다 | 주문 ↔ 메뉴, 학생 ↔ 과목 |

수업 노트의 예를 방향별로 풀어 쓰면 이렇다.

| 엔티티 쌍 | 방향 1 | 방향 2 | 결과 |
|-----------|--------|--------|------|
| 카테고리 : 메뉴 | 양식 카테고리에는 여러 메뉴가 속할 수 있다 | 하나의 메뉴는 여러 카테고리를 가질 수 없다 | 1:N |
| 회원 : 게시글 | 한 명이 여러 게시글을 쓴다 | 하나의 게시글은 작성자가 한 명이다 | 1:N |
| 학생 : 과목 | 한 학생이 여러 과목을 듣는다 | 한 과목을 여러 학생이 듣는다 | N:M → 수강으로 해소 |

### N:M은 왜 그대로 둘 수 없을까?

주문 101번이 "불타는 치킨 2개, 콜라 1개, 감자튀김 1개"라고 하자. 주문 테이블에 `menu_code` 칸 하나만 두면 이렇게 된다.

| order_code | order_date | total_price | menu_code | amount |
|------------|------------|-------------|-----------|--------|
| 101 | 2026-10-14 | 29700 | 1 | 2 |
| 101 | 2026-10-14 | 29700 | 7 | 1 |
| 101 | 2026-10-14 | 29700 | 9 | 1 |

문제는 두 가지다.

- 주문 1건이 3행이 되어 `order_code`를 기본키로 쓸 수 없다.
- 주문일자와 총금액이 메뉴 수만큼 중복 저장된다.

칸을 `menu_code1`, `menu_code2`로 늘리는 방법도 메뉴가 몇 개일지 모르니 한계가 있다. 해결책은 주문과 메뉴 사이에 **교차 엔티티 `주문상세(tbl_order_menu)`** 를 두는 것이다. 주문 한 건은 주문상세 여러 행을 갖고, 메뉴 하나도 주문상세 여러 행에 나타난다. 주문과 주문상세는 1:N, 메뉴와 주문상세도 1:N이 된다.

학생 ↔ 시험도 같다. 점수(`score`)는 학생에도 시험에도 속하지 않고 "어떤 학생이 어떤 시험을 본 결과"이므로, 학생별시험(StudentTest) 같은 교차 엔티티의 속성으로 둔다. 수강(학생 ↔ 과목)도 같은 중간 엔티티다.

### 필수와 선택, 그리고 카디널리티

| 구분 | 의미 | 외래키 | 예시 |
|------|------|--------|------|
| 필수 (Mandatory) | 자식이 부모 없이는 의미가 없다 | `NOT NULL` | 메뉴 → 카테고리: 카테고리가 없는 메뉴는 있을 수 없다 |
| 선택 (Optional) | 상대가 없어도 독립적으로 존재할 수 있다 | NULL 허용 | 카테고리 → 메뉴: 메뉴가 없는 "New" 카테고리를 만들 수 있다 |

폴더와 파일로 생각하면 쉽다. 파일은 반드시 어떤 폴더 안에 있어야 한다(필수). 하지만 빈 폴더를 만들려고 파일을 하나 넣을 필요는 없다(선택). 같은 관계라도 방향에 따라 필수성이 다르다.

**카디널리티(Cardinality)** 는 관계의 수치 범위(최소값~최대값)다. 최소값이 0이면 선택, 1이면 필수이고, 최대값이 1이면 하나, N이면 여러 개다. 예를 들어 `1..1 — 0..N`이면 "한쪽은 반드시 하나, 반대쪽은 없거나 여러 개"를 뜻한다.

| 관계 설명 | 카디널리티 | `menudb`에서의 구현 |
|-----------|------------|---------------------|
| 하나의 카테고리는 여러 메뉴를 가진다 | 1:N | `tbl_menu.category_code` → `tbl_category` |
| 한 주문은 여러 메뉴를, 한 메뉴는 여러 주문에 포함된다 | N:M → 해소 | `tbl_order_menu` |
| 한 결제는 여러 주문을 처리하고, 한 주문도 나눠 결제될 수 있다 | N:M → 해소 | `tbl_payment_order` |

1:N 관계의 외래키는 N 쪽에 둔다. 메뉴가 카테고리에 반드시 속한다면 `tbl_menu.category_code`는 `NOT NULL` 외래키여야 한다.

## 3. ERD는 어떤 표기법으로 그릴까?

ERD(Entity-Relationship Diagram)는 엔티티와 관계를 그림으로 표현해 구조의 정합성과 완전성을 검토하게 해 주고, 이후 논리·물리 모델의 기반이 된다. 같은 관계도 표기법에 따라 모양이 다르다.

| 표기법 | 특징 | 주요 사용처 |
|--------|------|-------------|
| 피터첸 (Peter Chen) | 개념적 모델링 중심의 전통적 E-R 모델 | 정보처리기사 등 시험, 이론 설명 |
| IE (Information Engineering) | 속성을 엔티티 박스 안에 적고 관계선 끝에 범위를 표시. 실무에서 가장 널리 쓴다 | ERwin, PowerDesigner, ERDCloud, dbdiagram.io |
| Barker | IE 계열의 한 분파. 속성 앞에 기호로 식별자와 필수 여부를 표시한다 | Oracle Designer 등 |

IE 표기법에서는 관계선 끝의 기호로 범위를 나타낸다. `|`는 1, `○`는 0, 갈라진 선(까마귀 발)은 N이다. 이 모양 때문에 Crow's Foot이라고 부른다.

Barker 표기법의 속성 기호는 수업 노트에서 이렇게 정리했다.

| 기호 | 의미 |
|------|------|
| `#` | PK, 식별자 |
| `*` | NOT NULL (필수) |
| `o` | NULL 가능 (선택) |

> 손으로 적은 노트에는 NULL 가능 기호가 `0`처럼 적혀 있다. 수업 자료의 Barker 표기법 설명은 속성 앞에 `#`, `*`, `o`를 붙인다고 되어 있으므로, 이 글에서는 영문자 `o`로 정리했다.

### `menudb`의 ERD

수업에서는 `menudb`를 IE 표기법으로 그렸다. 테이블 구성은 다음과 같다.

| 테이블 | 컬럼 | 키 |
|--------|------|----|
| `tbl_category` | `category_code`, `category_name`, `ref_category_code` | PK: `category_code`, FK: `ref_category_code` (상위 카테고리, 자기 참조) |
| `tbl_menu` | `menu_code`, `menu_name`, `menu_price`, `category_code`, `orderable_status` | PK: `menu_code`, FK: `category_code` |
| `tbl_order` | `order_code`, `order_date`, `order_time`, `total_order_price` | PK: `order_code` |
| `tbl_order_menu` | `order_code`, `menu_code`, `order_amount` | 복합 PK: (`order_code`, `menu_code`), 각각 FK |
| `tbl_payment` | `payment_code`, `payment_date`, `payment_time`, `payment_price`, `payment_type` | PK: `payment_code` |
| `tbl_payment_order` | `payment_code`, `order_code` | 복합 PK: (`payment_code`, `order_code`), 각각 FK |

관계는 "카테고리가 메뉴를 분류한다", "카테고리가 상위 카테고리를 가진다", "주문이 메뉴를 포함한다", "결제가 주문을 처리한다"로 읽는다. `tbl_order_menu`와 `tbl_payment_order`는 두 FK가 합쳐져 하나의 복합 PK가 되는 교차 엔티티다.

수업 자료의 `erDiagram`(Mermaid) 코드에는 `menudb`의 관계가 아래처럼 적혀 있다. Mermaid에서는 선 양 끝의 기호가 그쪽 엔티티의 최소·최대값을 뜻한다. 이 표기의 의미는 `||` 정확히 하나(1..1), `o|` 없거나 하나(0..1), `|{` 하나 이상(1..N), `o{` 없거나 여러 개(0..N)로 이해했다(`확인 필요`).

| 관계 (자료의 표기) | 읽는 법 | 한쪽 최소·최대 | 반대쪽 최소·최대 |
|--------------------|---------|----------------|------------------|
| `tbl_category` `\|\|--o{` `tbl_menu` ("분류한다") | 메뉴는 카테고리 정확히 1개에 속하고, 카테고리는 메뉴를 0개 이상 가진다 | 카테고리 쪽 1..1 | 메뉴 쪽 0..N |
| `tbl_category` `\|o--o{` `tbl_category` ("상위 카테고리") | 카테고리는 상위 카테고리를 없거나 1개 가지고, 하위 카테고리를 0개 이상 가진다 (자기 참조) | 상위 쪽 0..1 | 하위 쪽 0..N |
| `tbl_order` `\|\|--\|{` `tbl_order_menu` ("포함한다") | 주문상세 행은 주문 정확히 1건에 속하고, 주문은 주문상세를 1개 이상 가진다 | 주문 쪽 1..1 | 주문상세 쪽 1..N |
| `tbl_menu` `\|\|--o{` `tbl_order_menu` ("주문된다") | 주문상세 행은 메뉴 정확히 1개를 가리키고, 메뉴는 아직 주문되지 않았어도 된다 | 메뉴 쪽 1..1 | 주문상세 쪽 0..N |
| `tbl_payment` `\|\|--\|{` `tbl_payment_order` ("처리한다") | 결제연결 행은 결제 정확히 1건에 속하고, 결제는 주문을 1개 이상 처리한다 | 결제 쪽 1..1 | 결제연결 쪽 1..N |
| `tbl_order` `\|\|--o{` `tbl_payment_order` ("결제된다") | 결제연결 행은 주문 정확히 1건을 가리키고, 주문은 아직 결제되지 않았어도 된다 | 주문 쪽 1..1 | 결제연결 쪽 0..N |

정리하면 교차 엔티티(`tbl_order_menu`, `tbl_payment_order`) 쪽은 항상 부모 쪽이 필수(1..1)이므로 두 FK가 `NOT NULL`인 복합 PK가 된다. 반대로 메뉴와 주문은 교차 엔티티가 없어도 존재할 수 있어서(0..N) 아직 주문되지 않은 메뉴, 아직 결제되지 않은 주문을 저장할 수 있다.

> 이 글의 Mermaid 다이어그램은 이 블로그에서 렌더링되지 않는 것을 확인했기 때문에 쓰지 않고 표로 대신했다. 그림이 필요하면 ERDCloud 화면을 이미지로 올리는 방법이 있다.

## 4. 다 그린 ERD, 무엇을 검토할까?

바로 논리적 모델링으로 넘어가지 않고 설계자와 관계자가 구조와 업무 적합성을 검토한다.

| 검토 항목 | 확인 내용 |
|-----------|-----------|
| 엔티티의 명확성 | 모든 엔티티가 고유 식별자를 가지는가 |
| 속성의 완전성 | 주요 속성이 빠짐없이 포함되었는가 |
| 관계의 정합성 | 모든 엔티티 간 관계가 정확하게 정의되었는가 |
| 카디널리티의 명확성 | 1:1, 1:N, N:M 표현이 맞는가 |
| 관계의 필수성 | 선택/필수가 논리적으로 일관성 있게 설정되었는가 |
| 명명 규칙 | 엔티티와 속성 이름이 표준화되었는가 |
| 중복 및 유사 항목 제거 | 유사하거나 중복된 엔티티·속성이 통합되었는가 |
| 비즈니스 룰 반영 | 업무 정책이나 제약조건이 설계에 반영되었는가 |

수업의 신입 개발자 `menudb` 초안에는 문제가 4곳 숨어 있었다. 위 체크리스트로 찾은 항목을 정리하면 다음과 같다.

| 문제 | 위반한 검토 항목 |
|------|------------------|
| `tbl_menu`의 `MenuPrice`는 다른 컬럼과 달리 소문자 스네이크 표기가 아니다 | 명명 규칙 |
| `tbl_payment`에 PK(`payment_code`)가 없다 | 엔티티의 명확성 |
| `tbl_order`가 `menu_code` FK로 메뉴 1개만 가리킨다 | 카디널리티 (N:M을 해소하지 않음) |
| 카테고리 ↔ 메뉴를 "메뉴는 카테고리에 없거나 1개 속한다(선택)"로 그렸다 | 관계의 필수성 (메뉴는 카테고리에 반드시 속해야 함) |

> 실습 화면의 정답 해설은 자료에 없어서, 초안의 컬럼·관계 설명을 체크리스트와 대조해 찾은 4곳이다(`확인 필요`). 카테고리 자기 참조와 결제 ↔ 주문 연결(`tbl_payment_order`)은 문제가 없는 부분으로 보았다.

ERD 품질 검토는 혼자보다 팀 리뷰가 낫다. 관계의 방향과 카디널리티는 비즈니스 흐름에 따라 달라지므로, 규칙을 외우기보다 시나리오 중심으로 검토한다.

## 정리

1. 엔티티는 식별 가능, 여러 인스턴스, 의미 있는 속성, 독립 존재의 요건을 만족하는 것이고, 기본·중심·행위로 나뉜다.
2. 관계는 양방향으로 읽고 유형과 필수성(최소값)으로 정의한다. N:M은 교차 엔티티로 해소하고, 필수 관계의 외래키는 `NOT NULL`이다.
3. ERD는 IE 표기법을 많이 쓰며, 그린 뒤에는 체크리스트로 누락, 중복, 논리 오류를 검토한다.

다음에 볼 것은 논리적 모델링이다. 각 엔티티에 속성과 도메인을 정의하고 식별자(키)를 설계한다.

## 더 학습하면 좋은 개념

- **정규화(1NF~3NF)** — 교차 엔티티와 중복 제거를 이론적으로 설명한다. 오늘 N:M을 풀었던 이유를 정규형 관점에서 이해할 수 있다.
- **자기 참조 관계(Self Reference)** — 대댓글의 부모 댓글, 상위 카테고리처럼 같은 테이블을 가리키는 구조다. 계층형 데이터를 `JOIN`이나 재귀 쿼리로 조회할 때 필요하다.
- **식별 관계와 비식별 관계** — 부모의 PK가 자식의 PK에 포함되는지에 따른 구분이다. `tbl_order_menu`처럼 복합 PK가 생기는 이유를 설명한다.
- **ON DELETE / ON UPDATE 옵션** — 부모 행이 삭제될 때 자식 행의 처리 방식이다. 물리적 모델링에서 필수·선택 관계를 구현하는 데 쓴다.
- **대리키와 자연키** — 식별자를 업무 값으로 둘지 인위적 번호로 둘지의 선택이다. 논리적 모델링의 식별자 설계와 직결된다.
