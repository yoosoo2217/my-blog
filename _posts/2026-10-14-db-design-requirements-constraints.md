주문 테이블에 고객 연락처를 복사해 두었다고 해 보자. 회원 테이블에서 연락처를 고쳤는데 주문 테이블의 연락처는 그대로 남아 있다. 이 불일치는 쿼리를 잘 쓴다고 막아지지 않고, **테이블을 만들기 전의 설계**에서 막아야 한다.

> **TL;DR**
> - 설계는 데이터 중복·불일치를 막고, 틀린 값을 거르고, 접근 성능을 챙기기 위해 한다.
> - 설계는 요구사항 분석 → 개념적 → 논리적 → 물리적 모델링 4단계로 진행한다.
> - 요구사항 분석에서는 기능 문장에서 저장할 데이터를 찾고, 제약조건 6종과 데이터 사전으로 규칙을 정해 둔다.

환경: MySQL 8.0 기준 (`CHECK`는 8.0.16부터 강제됨). 실습 예시는 온라인 서점·주문 시스템이다.

## 1. 왜 테이블부터 만들면 안 될까?

시냇물의 디딤돌은 그냥 놓아도 되지만 큰 다리는 설계도가 있어야 짓는다. 데이터베이스도 같다. 잘못 설계하면 같은 정보가 여러 곳에 흩어지고, 틀린 값을 막지 못하고, 느려진다. 설계도의 역할은 복잡한 현실 세계를 단순화해서 목적에 맞게 정확히 표현하는 것이다. 잘 만든 모델은 의사소통, 문제 해결, 핵심 파악, 교육, 개발 등 여러 곳에서 기준점이 된다. 설계 이유는 세 가지다.

| 이유 | 설계 전 문제 | 설계로 얻는 것 |
|------|--------------|----------------|
| 중복·불일치 방지 | 같은 정보를 여러 테이블에 복사해 한쪽만 고치면 값이 어긋난다 | 한 곳에만 저장하고 나머지는 참조한다. 한 곳만 고쳐도 모두 반영된다 |
| 정합성·일관성 보장 | 테이블 간 관계가 불명확하거나 제약이 없으면 틀린 값도 저장된다 | 관계와 제약조건으로 잘못된 입력을 막는다 |
| 효율적인 접근·관리 | 조회와 조인이 느려진다 | 인덱스, 정규화, 관계 명세로 성능과 저장 공간을 챙긴다 |

### 중복이 불일치로 이어지는 과정

수업 실습에서는 회원 테이블과, 연락처를 복사해 저장한 주문 테이블을 두고 홍길동의 연락처를 바꿨다.

```sql
-- 예시 코드: 수업 실습을 SQL로 옮김
update tbl_member set phone = '010-9999-0000' where member_id = 1;
```

회원 테이블만 수정했으므로 `tbl_order`의 101번, 103번 주문에는 옛 번호 `010-1234-5678`이 남는다. 같은 사람의 연락처가 두 개가 된 것이다. 설계 후에는 주문이 `member_id`로 회원을 참조하고 연락처는 회원 테이블에만 둔다. 그러면 회원 테이블 한 곳만 고쳐도 모든 주문에서 새 번호가 보인다.

중복 제거는 정규화로 하고, 업무 정의에 기반한 명확한 식별자를 정하는 것이 핵심이다. 정규화는 이후 시간에 따로 배운다.

### 정합성과 일관성은 무엇이 다를까?

수업에서는 두 용어를 아래처럼 구분했다.

| 구분 | 의미 | 위반 예시 |
|------|------|-----------|
| 정합성 (Consistency) | 모든 테이블 간 데이터가 논리적으로 일치한다 | 회원 테이블에 없는 회원이 주문 테이블에 나온다 → 참조 무결성 위반 |
| 일관성 (Integrity) | 입력 데이터가 미리 정한 규칙을 만족한다 | 성별에 '남', '여' 외의 값이 들어간다 → 도메인 무결성 위반 |

> 영어 용어의 대응(Consistency/Integrity)은 수업 자료의 표기를 그대로 옮겼다. 이 용어는 자료마다 쓰임이 다를 수 있으므로, 두 위반 유형(참조 무결성, 도메인 무결성)을 기준으로 기억하는 편이 안전하다.

성능은 정합성과 트레이드오프 관계다. 설계 초기부터 접근 패턴과 조회 빈도를 함께 고려해야 균형을 잡을 수 있다.

## 2. 설계는 어떤 4단계로 진행될까?

설계는 테이블을 만드는 작업이 아니라, 현실 세계의 정보를 분석하고 구조화해서 DB에 맞게 표현하는 과정이다. 처음에는 코드 수준을 생각하지 않고 "현실 세계에서는 어떤 흐름인가?"를 떠올리며 단계적으로 모델링한다.

| 단계 | 핵심 질문 | 도구 | 산출물 |
|------|-----------|------|--------|
| 1. 요구사항 분석 | 어떤 데이터를 관리해야 하는가 | 기획자·개발자·사용자 협의 | 요구사항 정의서 |
| 2. 개념적 모델링 | 무엇이 존재하고 어떻게 연결되는가 | ERD | ERD(개체 관계도) |
| 3. 논리적 모델링 | 어떤 컬럼, 키, 제약으로 구조화하는가 | 정규화 | 논리 데이터 모델 |
| 4. 물리적 모델링 | 특정 DBMS에서 어떻게 구현하는가 | MySQL 등 DBMS | 물리 데이터 모델 + DDL 스크립트 |

온라인 서점을 예로 들면 단계별로 이렇게 바뀐다.

1. 요구사항 분석 : 회원, 주문, 도서, 카테고리를 관리해야 한다.
2. 개념적 모델링 : 엔티티 4개와 관계 3개(회원-주문 1:N, 주문-도서 N:M, 도서-카테고리 N:1)를 ERD로 그린다.
3. 논리적 모델링 : 각 엔티티의 컬럼과 키를 정한다.
4. 물리적 모델링 : MySQL 타입과 DDL로 옮긴다.

### 단계별 산출물에는 무엇이 들어갈까?

| 산출물 | 정의 | 포함하는 내용 |
|--------|------|---------------|
| 요구사항 정의서 (Requirements Specification) | 시스템이 수행할 기능과 다룰 데이터를 비즈니스 관점에서 기술한 문서. 사용자, 관리자, 기획자 등 이해관계자의 요구를 모아 정리하며, 설계의 출발점이 되는 가장 상위 문서다 | 관리해야 할 데이터 목록(회원, 주문, 상품 등), 업무 흐름(프로세스 다이어그램, 유스케이스 등), 필수 기능 목록(회원가입, 주문, 결제 등), 비기능 요건(보안, 성능, 용량 등) |
| ERD (Entity-Relationship Diagram) | 현실 세계의 개체와 개체 사이의 관계를 시각적으로 표현한 다이어그램. 개념적 모델링의 핵심 도구이며, 중복 제거와 세부 구조화 이전 단계의 결과물이다 | 엔티티(고객, 주문), 속성(이름, 주문일자), 관계, 카디널리티(1:1, 1:N, N:M) |
| 논리 데이터 모델 (Logical Data Model) | ERD의 구조를 바탕으로 테이블, 컬럼, 타입, 관계를 DBMS와 무관하게 정의한 결과물. 물리 모델로 넘어가기 전의 논리적 완성본이다 | 테이블과 컬럼 정의, 데이터 타입과 제약조건(NULL, UNIQUE 등), 기본키·외래키·대체키 정의, 정규화 수행 내역 |
| 물리 데이터 모델과 DDL (Physical Model & DDL) | 논리 모델을 실제 DBMS(MySQL, PostgreSQL, Oracle 등)의 특성에 맞게 변환한 결과물. SQL 문으로 실제 데이터베이스 객체가 된다 | DDL(`CREATE TABLE`, `CREATE INDEX` 등), 인덱스·파티션·뷰·트리거 등 성능 요소, 스키마 명명 규칙·저장소 정의·접근 권한, 테이블 간 참조 무결성 설정 |

각 단계는 순차적으로 진행되지만 앞 단계의 산출물이 다음 단계의 입력이 되므로 유기적으로 연결된다.

### 실무 팁

- 설계 단계를 건너뛰고 바로 테이블을 만들면 확장성, 정합성, 유지보수성에 문제가 생길 가능성이 높다.
- 항상 "현실 세계에선 어떤 흐름인가?"를 떠올리며, 처음에는 코드 수준을 생각하지 말고 단계적으로 모델링한다.
- ERDCloud 같은 도구로 설계 결과를 시각화하면 팀 내 소통이 쉬워진다.

## 3. 기능 문장에서 저장할 데이터를 어떻게 찾을까?

기능적 요구사항은 시스템이 수행해야 할 구체적인 작업이다. 행위 주체(사용자, 관리자)를 기준으로 "~할 수 있어야 한다" 형태로 쓴다.

- 사용자는 메뉴 목록을 조회할 수 있어야 한다.
- 사용자는 주문을 생성하고 주문 내역을 확인할 수 있어야 한다.
- 관리자는 메뉴 정보를 등록, 수정, 삭제할 수 있어야 한다.

여기서 **저장할 대상(명사)** 과 **기능(동사)** 을 구분하는 것이 핵심이다. 수업의 예시 문장이다.

| 문장 | 저장할 대상 (명사) | 기능 (동사) |
|------|--------------------|-------------|
| 고객은 상품을 장바구니에 담을 수 있어야 한다 | 고객, 상품, 장바구니 | 담는다 |
| 고객은 장바구니에 담긴 상품을 확인하고 결제를 진행할 수 있어야 한다 | 고객, 장바구니, 상품, 결제 | 확인, 진행 |
| 운영자는 상품의 판매 상태를 변경할 수 있어야 한다 | 운영자, 상품, 판매 상태 | 변경 |

### 헷갈렸던 점: "결제"는 동작인데 왜 저장 대상일까?

"결제를 진행한다"에서 결제는 동작처럼 보이지만, 결제일, 금액, 방식 등을 기록해야 하므로 저장 대상이다. 반면 "확인", "진행"은 기능을 설명하는 동작일 뿐이다. 그래서 명사 도출이 중요하다. 기능마다 필요한 데이터를 이렇게 이어서 볼 수 있다.

| 기능 | 저장해야 할 데이터 |
|------|--------------------|
| 결제 처리 | 결제일 `payment_date`, 결제시간 `payment_time`, 결제 금액 `payment_price`, 결제 방식 `payment_type` |

기능적 요구사항이 "무엇을 해야 하는가"라면, 데이터 요구사항은 "무엇을 저장해야 하는가"다. "주문에는 주문일자, 수량, 총금액이 필요하다"는 데이터 요구사항이고, "고객은 결제를 진행할 수 있어야 한다"는 기능적 요구사항이다. 데이터 요구사항에서는 저장 항목, 항목 간 연관 관계, 항목별 제약조건(필수 여부, 중복 허용 여부)을 식별한다.

## 4. 제약조건 6종은 각각 무엇을 막을까?

제약조건(Constraint)은 입력·갱신되는 데이터의 정확성, 일관성, 신뢰성을 보장하는 규칙이다. 설계 단계에서 정해 두면 구현 후의 데이터 오류를 미리 막는다.

| 제약조건 | 설명 |
|----------|------|
| `NOT NULL` | 해당 컬럼에 NULL 입력을 금지 |
| `UNIQUE` | 중복값 입력을 금지해 유일성 보장 |
| `PRIMARY KEY` | 행을 고유하게 식별. `NOT NULL` + `UNIQUE` |
| `FOREIGN KEY` | 다른 테이블의 값을 참조. 참조 무결성 보장 |
| `CHECK` | 값의 허용 범위를 지정 |
| `DEFAULT` | 값을 생략했을 때 적용할 기본값 |

수업 실습 테이블에는 여섯 가지가 모두 걸려 있다.

```sql
create table user_grade (
    grade_code int primary key,
    grade_name varchar(20)
);   -- (10, '일반회원'), (20, '우수회원'), (30, '특별회원')

create table tbl_user (
    user_no    int,
    user_id    varchar(255) not null,
    user_pwd   varchar(255) not null,
    phone      varchar(20),
    gender     varchar(3)  check (gender in ('남', '여')),
    age        int         check (age >= 19),
    grade_code int,
    country    varchar(20) default '한국',
    primary key (user_no),
    unique (phone),
    foreign key (grade_code) references user_grade (grade_code)
);
```

기존 회원은 `(1, 'user01', 'pass01', '010-1234-5678', '남', 25, 10, '한국')` 한 명이다. 이 상태에서 일부러 위반시킨 사례를 정리하면 다음과 같다.

| 시도한 입력 | 위반한 제약조건 | 이유 |
|-------------|-----------------|------|
| `user_pwd`에 NULL | `NOT NULL` | 비밀번호는 필수다 |
| 기존과 같은 `phone` | `UNIQUE` | 전화번호가 중복된다 |
| 기존과 같은 `user_no` 1 | `PRIMARY KEY` | 식별자가 중복된다 |
| `grade_code` 50 | `FOREIGN KEY` | `user_grade`에 없는 등급이다 |
| `gender`에 '남성' | `CHECK` | '남', '여'만 허용된다 |
| `age` 17 | `CHECK` | 19 이상이어야 한다 |
| `country` 생략 | 위반 아님 | `DEFAULT`가 '한국'을 채운다 |

수업 실습기는 MySQL 8.0과 같은 오류 메시지를 보여 주지만, 정확한 문구는 이 글에 옮기지 않았다.

### 헷갈리기 쉬운 지점

- **`DEFAULT`는 값을 생략했을 때만 적용된다.** `country`에 NULL을 직접 넣으면 NULL이 저장되고, 빈 문자열을 넣으면 빈 문자열이 저장된다.
- **`CHECK`는 MySQL 8.0.16부터 강제된다.** 그 이전 버전에서는 문법만 통과하고 조용히 무시되어 잘못된 값이 그대로 저장된다.
- **`DEFAULT`에 함수를 쓰려면 괄호가 필요하다.** `DATETIME`/`TIMESTAMP`의 `DEFAULT CURRENT_TIMESTAMP`만 괄호 없이 쓸 수 있다. 그 외에는 `DEFAULT (CURRENT_DATE)`처럼 감싼다(8.0.13 이상).
- 외래키에는 부모 키가 수정·삭제될 때의 처리 옵션(`ON UPDATE`, `ON DELETE`의 `CASCADE`, `SET NULL`, `RESTRICT`)이 있다. 수업에서는 미리 보기만 했고, 물리적 모델링 시간에 자세히 다룬다.

실무에서는 제약조건을 코드 속 유효성 검사보다 가능하면 **데이터베이스 차원**에서 설정한다. 일관성과 보안 측면에서 유리하기 때문이다. 예를 들어 회원 테이블의 성별 컬럼에 `CHECK`를 걸면 남과 여 외의 값을 강제로 막을 수 있다.

## 5. 데이터 사전은 왜 만들까?

데이터 사전(Data Dictionary)은 데이터 항목의 의미, 형식, 제약조건을 정의한 문서다. 우리가 무엇을 어떻게 부를지 미리 정해 두면 사람들 사이의 혼란이 없다. 같은 용어가 다른 의미로 쓰이거나, 다른 용어가 같은 의미로 쓰이는 일을 막기 위해 용어를 정의하고 하나의 명명 규칙으로 정리한다. 설계를 어떻게 하느냐에 따라 결과가 달라질 수 있으므로, 기준 용어를 먼저 정해 두어야 한다.

### 용어 정의와 표준화

| 용어명 | 정의 | 비고 |
|--------|------|------|
| 메뉴코드 | 메뉴를 고유하게 식별하는 코드 | PK |
| 주문가능상태 | 해당 메뉴의 주문 가능 여부 ('Y'/'N') | `CHECK` 제약조건 |
| 결제유형 | 현금, 카드, 계좌이체 중 하나의 값 | `CHECK` 또는 코드 테이블로 관리 |

### 데이터 항목 식별

기능 명세서나 화면 시나리오에서 필드를 뽑고, 업무 용어와 매핑한 뒤 중복을 정리한다. 이렇게 찾은 항목이 모델링에서 속성(Attribute)이 된다.

| 항목명 | 설명 |
|--------|------|
| `menu_name` | 메뉴명 |
| `menu_price` | 메뉴 가격 (단위: 원) |
| `category_code` | 메뉴가 속한 카테고리 코드 |
| `order_time` | 주문이 발생한 시각 |

### 데이터 형식과 규칙: 타입은 어떻게 고를까?

| 분류 | 타입 | 쓰임 |
|------|------|------|
| 문자열 | `VARCHAR(n)`, `CHAR(n)`, `TEXT` | 가변 길이 / 고정 길이 / 긴 문자열 |
| 숫자 | `INT`, `BIGINT`, `DECIMAL(P,S)` | 정수 / 소수점·정밀도가 필요한 값 (금액은 `DECIMAL`) |
| 날짜/시간 | `DATE`, `DATETIME`, `TIMESTAMP` | 날짜만 / 입력값 그대로 저장(기본 권장) / UTC 변환 저장, 1970~2038년 범위 |
| 상태값 | `BOOLEAN`, `CHAR(1)` + `CHECK` | MySQL의 `BOOLEAN`은 `TINYINT(1)`의 별칭 |

타입 고르기 실습의 정답은 이렇게 된다.

| 항목 | 알맞은 타입 |
|------|-------------|
| 회원 이름(최대 30자) | `VARCHAR(30)` |
| 상품 상세 설명(수천 자 이상) | `TEXT` |
| 결제 금액(할인율로 소수점 발생) | `DECIMAL` |
| 주문 가능 여부('Y' 또는 'N') | `CHAR(1)` + `CHECK` |
| 주문이 들어온 시각 | `DATETIME` |
| 회원 생년월일 | `DATE` |
| 장바구니 담은 수량 | `INT` |

> 위 정답은 수업 실습의 보기에서 고른 유형을 기준으로 정리했다. 보기 구성은 `확인 필요`.

이 내용을 정리한 데이터 정의서 예시는 다음과 같다.

| 항목명 | 데이터 타입 | 길이 | NULL | 제약조건 | 예시값 |
|--------|-------------|------|------|----------|--------|
| `menu_code` | `INT AUTO_INCREMENT` | - | NO | `PRIMARY KEY` | 1 |
| `menu_name` | `VARCHAR` | 30 | NO | - | 불타는 치킨 |
| `menu_price` | `INT` | - | NO | `CHECK (>= 0)` | 9900 |
| `orderable_status` | `CHAR` | 1 | NO | `CHECK ('Y', 'N')` | Y |
| `payment_type` | `VARCHAR` | 6 | NO | '현금', '카드', '이체' 등 | 카드 |
| `add_time` | `DATETIME` | - | YES | `DEFAULT CURRENT_TIMESTAMP` | 2025-05-20 10:32 |

이 문서를 ERD 작성 전에 Notion, 엑셀 등으로 공유해 두면 모델링 단계에서 속성명, 타입, 제약조건을 일관되게 쓸 수 있다.

## 정리

1. 설계는 중복·불일치 방지, 정합성 확보, 성능 최적화를 위해 하고, 요구사항 분석 → 개념적 → 논리적 → 물리적 모델링 순서로 진행한다.
2. 기능 문장에서 명사는 저장 대상, 동사는 기능이다. 데이터 요구사항은 "무엇을 저장하는가"에 답한다.
3. 제약조건 6종은 데이터베이스 차원에서 잘못된 값을 막고, 데이터 사전은 용어, 타입, 길이, 제약을 정리해 소통한다.

다음에 볼 것은 개념적 모델링이다. 오늘 찾은 데이터 후보로 엔티티와 관계를 정하고 ERD를 그린다.

## 더 학습하면 좋은 개념

- **정규화(Normalization)** — 중복을 구조적으로 없애는 방법이다. 오늘 본 연락처 중복 문제를 설계 규칙으로 해결하는 방법이 여기에 있다.
- **참조 무결성 옵션(`ON DELETE`, `ON UPDATE`)** — 부모 행이 사라질 때 자식 행을 어떻게 할지 정한다. 외래키를 걸 때 이 옵션까지 함께 정해야 참조 무결성이 유지된다.
- **MySQL 버전별 차이** — `CHECK`(8.0.16)와 표현식 `DEFAULT`(8.0.13)처럼 버전에 따라 동작이 달라진다. 구버전 환경에서 설계를 옮길 때 문제가 없는지 판단하는 기준이 된다.
- **`DECIMAL`과 부동소수점의 차이** — 금액에 `DECIMAL`을 권하는 이유를 이해하려면 알아야 한다.
- **`TIMESTAMP`의 2038년 문제** — `DATETIME`을 기본으로 권하는 이유와 연결된다.
