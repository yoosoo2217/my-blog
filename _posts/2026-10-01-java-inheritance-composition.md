## 1. 상속이란

부모 클래스가 가지는 멤버(필드, 메서드)를 자식 클래스가 물려받아 자신의 멤버인 것처럼 사용할 수 있도록 만든 기술이다. 단, **생성자는 물려받지 않는다.** 멤버 외에도 부모 클래스의 **타입 또한 상속**되는데, 이게 다형성의 문법적 토대가 된다. Java는 **단일상속**(자식 클래스는 하나의 부모 클래스만 가짐)만 지원하고, `extends` 키워드를 사용한다.

### 1-1. 상속의 장단점

- **장점**
    1. **코드 재사용성 증가** — 공통 기능을 상위 클래스에 정의하면 하위 클래스에서 중복 제거 가능.
    2. **구조화된 계층 설계 가능** — is-a 관계로 객체의 구조와 역할을 자연스럽게 표현 가능.
    3. **다형성과 함께 사용 시 유연한 프로그래밍 가능** — 부모 타입으로 다양한 자식 객체를 처리 가능.
- **단점**
    1. **높은 결합도(coupling)** — 하위 클래스는 상위 클래스에 강하게 의존하게 됨.
    2. **유연성 저하** — 부모 클래스를 하나만 상속 가능(Java는 다중 상속 불가).
    3. **상속 계층이 깊어지면 유지보수 어려움**.

### 1-2. 깊은 상속 계층의 문제점

```java
class A { ... }
class B extends A { ... }
class C extends B { ... }
class D extends C { ... }
```

하위 클래스 `D`는 `A`~`C`의 모든 설계를 암묵적으로 의존하게 된다. 어느 한 클래스만 수정되어도 모든 하위 클래스에 영향이 갈 수 있어서 디버깅과 유지보수 난이도가 급증한다. **"코드 재사용이 아니라 코드 복잡도 전파"**가 될 수 있다.

### 1-3. 상속 관계에서의 결합도

```java
class Printer {
    void print() { System.out.println("출력!"); }
}

class FancyPrinter extends Printer {
    void printFancy() {
        print();
        System.out.println("★ 장식 추가 ★");
    }
}
```

하위 클래스는 상위 클래스의 **구현에 강하게 결합**된다. 부모 클래스가 바뀌면 자식 클래스도 영향을 받는다. 부모의 `print()`가 변경되면, `FancyPrinter`의 동작에도 의도치 않은 변화가 생길 수 있다.

> 결론: 상속은 "강력하지만 신중하게" 써야 한다. 공통된 기능 공유, 정확한 is-a 관계, 변하지 않는 구조라면 적합하지만, 잘못 쓰면 변경에 취약하고 유연하지 못한 설계가 된다.

## 2. 컴포지션(Composition)

### 2-1. 컴포지션이란

객체 내부에 **다른 객체를 필드로 포함(has-a 관계)**해서 기능을 재사용하거나 역할을 위임하는 설계 방식이다.

```java
class Engine {
    void start() {
        System.out.println("엔진이 켜졌습니다.");
    }
}

class Car {
    private Engine engine = new Engine();

    void drive() {
        engine.start(); // 엔진에게 기능 위임
        System.out.println("자동차가 움직입니다.");
    }
}
```

`Car`는 `Engine`을 "상속"하지 않고 **포함**하고 있다.

- Car is-a Engine (X)
- Engine is-a Car (X)
- **Car has-a Engine (O)**
- Engine has-a Car (X)

동작은 그대로 재사용되지만, 구조는 느슨하게 유지된다.

### 2-2. 컴포지션이 더 적합한 경우

- 자식 클래스가 부모의 모든 기능을 필요로 하지 않을 때 — 상속하면 불필요한 메서드까지 강제로 가지게 된다.
- 변경 가능성이 높은 구조일 때 — 컴포지션은 구현을 교체하거나 조립하기 쉽다.
- 여러 역할을 동시에 해야 할 때 — 상속은 1개만 가능하지만, 컴포지션은 여러 객체를 포함할 수 있다.

### 2-3. 상속을 컴포지션으로 리팩토링하기

**기존 상속 설계**

```java
class Logger {
    void log(String msg) {
        System.out.println("[LOG] " + msg);
    }
}

class Service extends Logger {
    void process() {
        log("처리 시작");
        // ...
    }
}
```

`Service`가 `Logger`를 **상속**하고 있어서 결합도가 높고, 다른 종류의 로깅이 필요해지면 유연하게 대응할 수 없다.

**컴포지션으로 변경**

```java
class Service {
    private Logger logger;

    public Service(Logger logger) {
        this.logger = logger;
    }

    void process() {
        logger.log("처리 시작");
        // ...
    }
}
```

`Logger`를 필드로 **포함**하고 외부에서 주입받는 구조로 바꾸면, 추후 필요할 때 다른 `Logger`로 유연하게 교체할 수 있다.

### 2-4. 위임(Delegation) 패턴

위임은 **자신이 직접 처리하지 않고, 포함된 객체에게 기능을 전달**하는 구조다. 컴포지션을 통해 기능을 외부 객체에 위임하면 코드 재사용과 유연성을 동시에 얻을 수 있다.

```java
class Printer {
    void print() {
        System.out.println("출력!");
    }
}

class Report {
    private Printer printer = new Printer();

    void printReport() {
        printer.print(); // 본인이 직접 구현하거나 상속받지 않고 프린터에게 기능 위임
    }
}
```

`Report`는 `Printer`를 상속하지 않았지만, 필요한 기능만 위임받아 사용한다.

### 2-5. 상속 vs 컴포지션

| 항목 | 상속 (Inheritance) | 컴포지션 (Composition) |
|---|---|---|
| 관계 | is-a (A는 B이다) | has-a (A는 B를 가진다) |
| 유연성 | 낮음 (강한 결합) | 높음 (느슨한 결합) |
| 재사용 | 전체 기능 상속 | 필요한 기능만 포함 |
| 다중 역할 | 불가능 (단일 상속) | 가능 (여러 객체 조합) |
| 변경 대응 | 구조 변경에 취약 | 구현 교체가 쉬움 |

> 결론: 가능한 상속보다 컴포지션을 우선 고려하는 것이 객체지향적인 설계 원칙이다. 상속은 강력하지만 위험할 수 있고, 컴포지션은 유연하고 안전하다.

## 오늘 정리

- 상속은 부모의 필드·메서드·타입을 물려받아 코드 재사용과 구조화된 설계(is-a)를 가능하게 하지만, 상속 계층이 깊어질수록 결합도가 높아지고 유지보수가 어려워진다는 걸 `A`→`B`→`C`→`D` 예시로 확인했다.
- 컴포지션은 다른 객체를 필드로 포함(has-a)하는 방식으로, `Logger`를 상속받던 `Service`를 필드로 주입받는 구조로 바꿔보면서 결합도가 낮아지는 걸 직접 비교했다.
- 위임 패턴은 컴포지션을 활용해 기능을 포함된 객체에게 넘기는 구조이고, 가능하면 상속보다 컴포지션을 우선 고려하는 게 객체지향적인 설계 원칙이라는 걸 정리했다.

이번 OOP 묶음 글들을 통해, 추상화로 공통점을 뽑아내고, 다형성으로 하나의 타입처럼 다루고, 캡슐화로 내부를 숨기고, 상속·컴포지션으로 구조를 짜는 것까지 — 객체지향의 핵심 요소들이 서로 어떻게 맞물리는지 전체적으로 훑어본 셈이다.

## 더 학습하면 좋은 개념

- **SOLID 원칙 전체** — 이번 OOP 묶음 글 여러 곳에서 리스코프 치환 원칙, 단일 책임 원칙이 부분적으로 언급됐는데, 나머지 원칙(개방-폐쇄, 인터페이스 분리, 의존관계 역전)까지 묶어서 정리하면 좋을 것 같다.
- **디자인 패턴** — 오늘 배운 위임 패턴처럼, 상속·컴포지션을 조합해서 자주 쓰이는 패턴(전략 패턴, 데코레이터 패턴 등)이 더 있다고 들어서 다음 단계로 알아보고 싶다.
- **다중 인터페이스 구현** — [추상화 글]({{ site.baseurl }}/java-abstraction-interfaces.html)에서 "인터페이스는 다중 구현이 가능하다"고 했는데, 실제로 한 클래스가 여러 인터페이스를 구현하는 코드를 직접 짜보면서 상속의 단일 상속 제약과 비교해보고 싶다.
