회원 테이블에 5명이 들어 있고, 이름과 생년월일을 묶으면 지금은 모든 행이 구분된다. 그렇다고 이 조합을 기본키로 써도 될까? 동명이인이 같은 날 태어나는 순간 깨진다. 이 글은 **속성을 어떻게 정의하고, 행을 구분할 키를 어떤 기준으로 고르는지** 정리한다.

> **TL;DR**
> - 논리적 모델링은 개념 모델을 상세화해 엔티티마다 속성과 식별자를 정하는 단계다.
> - 속성은 분해 여부와 특성으로 분류하고, 도메인과 NULL 허용 여부는 업무 규칙으로 정한다.
> - 후보키 중 유일성, 최소성, 불변성, 단순성을 기준으로 기본키를 고르고, 나머지는 대체키로 `UNIQUE`를 건다.

환경: MySQL 8.0 기준. 앞선 글 [설계 2: 개념적 모델링]({{ site.baseurl }}/db-design-conceptual-modeling-erd.html)에서 이어진다.

## 1. 논리적 모델링에서는 무엇을 할까?

논리적 모델링은 개념 모델을 상세화하는 단계다. 엔티티마다 전체 속성을 도출하고, 아직 드러나지 않은 엔티티와 관계를 찾고, 중복을 제거하는 정규화도 이 단계에서 한다. 정규화는 다음 글에서 다룬다.

이 단계부터는 논리 용어와 물리 용어가 섞여 나온다. 짝을 알아 두면 헷갈리지 않는다.

| 논리적 모델링 | 물리적 모델링 (DB) | 예시 |
|---------------|--------------------|------|
| 엔티티 (Entity) | 테이블 (Table) | 회원 → `tbl_member` |
| 속성 (Attribute) | 컬럼 (Column) | 회원명 → `member_name` |
| 인스턴스 (Instance), 튜플 | 행 (Row), 레코드 | 회원 한 명의 데이터 |
| 식별자 (Identifier) | 기본키 (Primary Key) | 회원번호 → `member_id` |
| 관계 (Relationship) | 외래키 (Foreign Key) | 주문의 회원번호 → `member_id` FK |

## 2. 속성은 무엇을 기준으로 정의할까?

속성은 엔티티의 구성 요소이자 데이터를 저장하는 최소 단위다. 각 속성은 하나의 데이터 항목이고, 물리 모델에서 컬럼이 된다. 그래서 정확하고 일관되게 정의해야 한다.

| 설계 요소 | 설명 |
|-----------|------|
| 속성명 | 명확하고 일관된 명명 규칙을 적용한다 (`menu_name`, `order_date`) |
| 데이터 의미 | 의미가 모호하지 않고 명확하게 설명될 수 있어야 한다 |
| 데이터 형식 | 정해진 도메인 또는 표준 데이터 타입을 기반으로 정의한다 |
| 필수 여부 | 반드시 입력되어야 하는 값인지 정한다 (`NOT NULL` 여부로 연결) |
| 기본값 | 생략 시 자동으로 입력될 값이다 (예: `CURRENT_TIMESTAMP`) |

### 속성의 종류: 분해 여부와 특성

속성은 두 기준으로 나눈다. 값을 더 쪼갤 수 있는가(분해 여부)와 값이 어디서 오는가(특성)다.

| 분해 여부 | 설명 | 예시 |
|-----------|------|------|
| 단일 속성 | 하나의 의미로 구성된 단일 데이터 항목 | 부서명, 상품명, 수량, 단가 |
| 복합 속성 | 두 개 이상의 하위 속성으로 나눌 수 있는 속성 | 주소(시/구/동), 전화번호(국번/번호) |
| 다가 속성 | 하나의 속성이 여러 값을 가질 수 있는 구조 (1:N 데이터를 담고 있음) | 연락처 여러 개, 주문 메뉴 목록, 결제 내역 |

| 특성 | 설명 | 예시 |
|------|------|------|
| 기초 속성 | 엔티티의 본질적인 속성으로, 그 자체로 객체를 설명한다 | 고객명, 상품명, 수량, 단가 |
| 관계 속성 | 다른 엔티티와의 관계를 나타내며 보통 외래키로 구현한다 | 주문의 고객번호(FK), 상품번호(FK) |
| 추출 속성 | 다른 속성들의 연산으로 만들어지는 속성 | 주문금액 = 수량 × 단가 |

쇼핑몰 속성을 두 기준으로 분류해 보면 다음과 같다.

| 속성 | 분해 여부 | 특성 |
|------|-----------|------|
| 배송지 주소 (시/구/동/상세주소) | 복합 | 기초 |
| 주문 테이블의 회원번호 | 단일 | 관계 |
| 주문금액 (수량 × 단가) | 단일 | 추출 |
| 회원의 연락처들 (집, 휴대폰, 회사) | 다가 | 기초 |
| 상품명 | 단일 | 기초 |
| 장바구니 수량 | 단일 | 기초 |

> 이 표는 위 정의에 맞춰 직접 분류한 결과다. 수업 실습의 채점 결과와 같은지는 `확인 필요`.

### 복합·다가 속성은 결국 어떻게 될까?

관계형 모델에서는 제1정규형(1NF)에 따라 한 칸에는 값이 하나만 들어가야 한다. 그래서 복합 속성은 필요에 따라 하위 속성으로 쪼개고, 다가 속성은 별도 엔티티로 분리한다. 다음 글 정규화의 첫 단계가 이 작업이다.

## 3. 도메인은 왜 속성마다 정의할까?

도메인(Domain)은 속성이 가질 수 있는 값의 허용 범위나 규칙 집합이다. 데이터 타입, 길이, 허용 값, 기본값, 제약조건을 묶어 정의해 데이터 일관성을 보장한다. 수업의 두 예시는 이렇다.

| 항목 | `orderable_status` (주문 가능 상태) | `payment_type` (결제 구분) |
|------|-------------------------------------|----------------------------|
| 타입 | `CHAR(1)` | `VARCHAR(6)` |
| 허용 값 | 'Y', 'N'만 | '현금', '카드', '이체', '기프티콘' |
| 기본값 | 'N' (등록 직후 일반 사용자에게 실수로 노출되지 않도록) | 없음 (반드시 입력) |

이 도메인에 비춰 값을 넣어 보면 이렇게 판정할 수 있다.

| 값 | 도메인 안인가 | 이유 |
|----|---------------|------|
| `orderable_status = 'Y'` | 안 (허용) | 허용 값이다 |
| `orderable_status = 'YES'` | 밖 (불허) | 허용 값이 'Y', 'N'뿐이고 길이도 1을 넘는다 |
| `orderable_status = 'y'` | `확인 필요` | 소문자는 허용 값에 없다. 다만 MySQL의 문자열 비교는 콜레이션에 따라 대소문자를 구분하지 않을 수 있다 |
| `payment_type = '기프티콘'` | 안 (허용) | 허용 값에 있다 |
| `payment_type = '신용카드'` | 밖 (불허) | 허용 값에 없고 `VARCHAR(6)`에는 들어가지만 도메인 규칙에 어긋난다 |

> 소문자 `'y'`와 콜레이션 관련 설명은 수업 자료에 없고 내가 보충했다. 직접 실행한 결과가 아니므로 `확인 필요`.

### 속성이 많을 때 도메인은 어떻게 뽑을까?

속성이 많으면 하나씩 도메인을 정하기 어렵다. 수업에서는 (옵션으로) 공통 규칙을 찾아 도메인을 도출하는 방법을 소개했다.

1. 모든 속성을 엔티티별로 나열한다. (회원명, 상품명, 주문일자, 가입일자, 상품가격, 결제금액 …)
2. 합성명사를 분리한다. (회원+명, 상품+가격, 가입+일자 …)
3. 공통으로 등장하는 명사를 모은다. (명, 일자, 금액/가격 …)
4. 공통 명사를 도메인으로 정하고 속성을 할당한다. (이름 도메인, 날짜 도메인, 금액 도메인)
5. 도메인별로 데이터 타입과 길이를 지정한다. (날짜 도메인 = `DATE`, 금액 도메인 = `DECIMAL(12,2)`)

이렇게 하면 "날짜는 어떤 테이블에서든 같은 타입"처럼 프로젝트 전체의 일관성이 생긴다.

## 4. 속성에 NULL을 허용할지 어떻게 정할까?

NULL은 "값이 없다"는 상태로, 알 수 없음(UNKNOWN) 또는 해당 없음을 뜻한다. 0이나 빈 문자열과는 다르다. 아래 세 질문으로 판단한다.

| 판단 질문 | 결정 |
|-----------|------|
| 업무상 반드시 필요한 값인가? | 주문일자, 사용자 ID → `NOT NULL` |
| 생성 시점에는 알 수 없는 값인가? | 회원 탈퇴일, 승인일 → NULL 허용이 필요할 수 있다 |
| 파생되거나 계산 가능한 값인가? | 계산 가능하면 저장을 생략하고, 저장한다면 NULL 또는 기본값을 설정한다 |

이 질문을 적용해 실습 항목을 판단하면 이렇다.

| 항목 | 결정 | 근거 |
|------|------|------|
| 로그인 아이디 | `NOT NULL` | 업무상 반드시 필요하다 |
| 회원 탈퇴일 | NULL 허용 | 가입 시점에는 알 수 없다 |
| 가입일시 (생략하면 현재 시각) | `NOT NULL` + `DEFAULT` | 값은 항상 있고 생략 시 자동으로 채운다 |
| 게시글 관리자 승인일 | NULL 허용 | 작성 시점에는 승인 전이다 |
| 메뉴 주문 가능 상태 (등록 시 'N') | `NOT NULL` + `DEFAULT` | 값은 항상 있고 등록 시 'N'이 들어간다 |
| 회원 자기소개 (선택 입력) | NULL 허용 | 입력하지 않아도 된다 |

> 이 표도 위 판단 질문으로 직접 정리한 결과이고, 수업 실습 정답과의 일치 여부는 `확인 필요`.

NULL 허용 속성이 너무 많으면 데이터 해석이 모호해져 품질이 떨어진다. `NOT NULL` + `DEFAULT` 조합은 값 누락을 막으면서 입력도 편하게 해 준다.

## 5. 키는 어떤 종류가 있을까?

식별자(Identifier)는 엔티티의 인스턴스를 하나씩 구분해 주는 속성이고, 물리 모델에서 기본키가 된다. 키는 아래 순서로 좁혀진다.

1. 슈퍼키 : 유일하기만 하면 되는 모든 조합. 예) {회원번호, 이름}, {이메일, 전화번호}
2. 후보키 : 슈퍼키 중 유일성과 최소성을 만족하는 조합. 더 뺄 열이 없다
3. 기본키(PK) : 후보키 중 대표로 선택한 1개
4. 대체키(AK) : 기본키로 선택되지 않은 나머지 후보키. `UNIQUE`로 관리한다

| 키 | 정의 | 회원 예시 |
|----|------|-----------|
| 후보키 (Candidate Key) | 행을 유일하게 식별할 수 있는 최소한의 속성 또는 속성 집합. 여러 개일 수 있다 | 회원번호, 이메일, 전화번호 |
| 기본키 (Primary Key) | 후보키 중 대표로 선택한 하나. `NOT NULL` + `UNIQUE` | 회원번호 |
| 대체키 (Alternate Key) | 기본키로 선택되지 않은 나머지 후보키. `UNIQUE`로 관리한다 | 이메일, 전화번호 |
| 외래키 (Foreign Key) | 다른 엔티티의 기본키를 참조하는 속성. 관계 속성의 구현 방식이다 | 주문 테이블의 회원번호 |

메뉴로 예를 들면 `menu_code`는 메뉴를 고유하게 식별하므로 후보키다. 하지만 `menu_name`은 같은 이름이 생길 수 있어 후보키로 부적절하다. 실무에서는 대개 단순한 정수형 코드를 기본키로 두고, 이메일 같은 자연키는 `UNIQUE` 제약으로 관리한다.

### 헷갈렸던 점: 지금 유일하면 후보키일까?

키 감별기의 회원 테이블에는 아래 5건이 들어 있다.

| 회원번호 | 이메일 | 전화번호 | 이름 | 생년월일 | 가입일 |
|----------|--------|----------|------|----------|--------|
| 1 | kim@mail.com | 010-1111-2222 | 김민수 | 2001-03-02 | 2026-03-02 |
| 2 | lee@mail.com | 010-3333-4444 | 이지은 | 2002-07-15 | 2026-03-02 |
| 3 | park@mail.com | 010-5555-6666 | 김민수 | 2000-11-20 | 2026-03-05 |
| 4 | choi@mail.com | 010-7777-8888 | 최유리 | 2001-03-02 | 2026-03-09 |
| 5 | jung@mail.com | 010-9999-0000 | 정하늘 | 2003-01-30 | 2026-03-09 |

이름이 같은 회원(김민수)과 생년월일이 같은 회원(2001-03-02)은 있지만 `이름 + 생년월일` 조합은 지금 5건에서 겹치지 않는다. 하지만 후보키는 **데이터가 아니라 업무 규칙으로** 정한다. 업무 규칙은 아래와 같았다.

| 속성 | 업무 규칙 | 후보키 여부 |
|------|-----------|-------------|
| 회원번호 | 시스템이 하나씩 부여한다 | 후보키 |
| 이메일 | 중복 가입을 막기 위해 회원마다 달라야 한다 | 후보키 |
| 전화번호 | 중복 가입을 막기 위해 회원마다 달라야 한다 | 후보키 |
| 이름, 생년월일, 가입일 | 다른 회원과 같을 수 있다 | 후보키 아님 (조합도 규칙으로 보장되지 않는다) |

현재 데이터에서 유일하다는 사실만으로는 후보키가 되지 않는다. 동명이인이 같은 날 태어나는 일은 언제든 생길 수 있다.

최소성도 구분해 둬야 한다. {학번, 이름}으로 모든 학생을 구분할 수 있어도 학번만으로 충분하다면, {학번, 이름}은 후보키가 아니라 최소성을 위반한 **슈퍼키**다.

## 6. 기본키는 어떤 기준으로 고를까?

| 기준 | 의미 | 예시 |
|------|------|------|
| 유일성 (Uniqueness) | 모든 행에서 값이 달라야 하고 중복이 없어야 한다 | 학번, 사원번호는 사람마다 다르다 |
| 최소성 (Irreducibility) | 꼭 필요한 최소한의 속성으로만 구성한다. 하나라도 빼면 더 이상 유일하지 않아야 한다 | [학번 + 이름] 대신 [학번]만으로 충분하면 이름은 뺀다 |
| 불변성 (Stability) | 한 번 정해진 값이 바뀌지 않아야 한다. 기본키가 바뀌면 이를 참조하는 모든 외래키도 바꿔야 한다 | 전화번호, 이메일은 바뀔 수 있어 부적합하다 |
| 단순성 (Simplicity) | 가능하면 단일 속성으로 한다. 복합키는 꼭 필요할 때만 쓴다 | [이름 + 생년월일 + 반 + 번호]보다 [학번] |

### 복합키는 언제 쓸까?

복합키(Composite Key)는 조합키 또는 합성키라고도 한다. 하나의 속성만으로 기본키 역할을 할 수 없을 때 여러 후보 속성을 묶어 기본키로 쓴다. 장바구니가 대표적이다. 고객번호만으로도, 상품번호만으로도 행을 구분할 수 없지만 둘을 묶으면 "이 고객이 담은 이 상품"이 하나로 정해진다.

장바구니는 고객과 상품의 N:M 관계를 해소하는 연관 엔티티이고, 복합키를 이루는 속성들은 외래키 역할도 겸하는 경우가 많다.

| 엔티티 | 속성 | 키 |
|--------|------|----|
| 고객 | `고객번호`, `고객명`, `전화번호` | `고객번호` PK, `전화번호` AK |
| 장바구니 | `고객번호`, `상품번호`, `수량` | (`고객번호`, `상품번호`) 복합 PK, 각각 FK |
| 상품 | `상품번호`, `상품명`, `가격` | `상품번호` PK |

## 7. 대체키와 외래키는 어떻게 쓸까?

대체키는 업무상 중요한 의미가 있지만 기본키 기준(불변성, 단순성 등)에 맞지 않아 제외된 후보키다. 위 고객 엔티티에서 고객번호는 시스템 내부용 기본키(`AUTO_INCREMENT` 정수 등)이고, 전화번호는 대체키로서 `UNIQUE`로 중복만 막는다.

```sql
-- 예시 코드: 수업 자료의 고객 엔티티를 옮긴 것, 직접 실행해 확인하지는 않음
create table customer (
    customer_id   int auto_increment primary key,
    customer_name varchar(30) not null,
    phone         varchar(20) unique
);
```

전화번호, 이메일, 주민등록번호는 중복 방지를 위해 대체키로 둘 수는 있지만, 변경 가능성과 개인정보 보호 문제 때문에 기본키로는 쓰지 않는 것이 일반적이다.

외래키는 다른 엔티티의 기본키를 참조하는 속성이다. 관계 속성의 구현 방식이자 엔티티 간 종속성을 표현한다. 장바구니는 고객과 상품 두 테이블의 기본키를 모두 외래키로 참조하면서, 그 둘을 묶어 복합 기본키로도 쓴다.

```sql
-- 예시 코드: 확인 필요
create table cart (
    customer_id int,
    product_id  int,
    quantity    int,
    primary key (customer_id, product_id),
    foreign key (customer_id) references customer (customer_id),
    foreign key (product_id)  references product (product_id)
);
```

> `product` 테이블은 위 예시에 포함하지 않았다. 실행하려면 `product(product_id)`가 먼저 있어야 한다.

## 정리

1. 속성은 분해 여부(단일/복합/다가)와 특성(기초/관계/추출)으로 분류한다. 복합·다가 속성은 정규화에서 분해한다.
2. 도메인은 타입, 길이, 허용 값, 기본값을 묶은 규칙이고, NULL 허용 여부는 업무상 필수인지와 생성 시점에 알 수 있는지로 판단한다.
3. 후보키는 업무 규칙으로 정하고, 그중 유일성, 최소성, 불변성, 단순성을 따져 기본키를 고른다. 나머지는 대체키로 두어 `UNIQUE`를 건다.

다음에 볼 것은 정규화다. 수강신청 표 하나를 비정규형부터 쪼개며, 오늘 배운 키와 종속 관계가 중복 제거에 어떻게 쓰이는지 확인한다.

## 더 학습하면 좋은 개념

- **함수 종속(Functional Dependency)** — 어떤 값이 다른 값에 의해 정해지는 관계다. 후보키와 정규화의 기준이 되는 개념이다.
- **제1정규형(1NF)** — 한 칸에 값이 하나만 들어가야 한다는 규칙이다. 복합·다가 속성을 분해하는 이유를 설명한다.
- **자연키와 대리키(Surrogate Key)** — 업무 값을 키로 쓸지 인위적 번호를 쓸지의 선택이다. 기본키 선정 기준과 직결된다.
- **`AUTO_INCREMENT`** — 정수 기본키를 시스템이 자동 부여하는 MySQL 기능이다. 단일 키 전략의 표준 선택이다.
- **`NOT NULL` + `DEFAULT` 조합** — 값 누락을 막으면서 입력도 편하게 하는 방법이다. 물리적 모델링에서 그대로 쓰인다.
